# 相关工作重新评估（2026-08-27）

结论先行：**这个方向研究层面已经很拥挤，支柱4/5 想填的具体空子基本都被 2024-2026 的论文占了；但项目定位从一开始就不是发论文，是求职作品集（目标：SWE / Agent 交叉岗位），所以核心结论不是"项目没价值"，而是"叙事要从研究贡献改成系统工程能力"。**

## 2. 一个需要立刻改的具体错误

`papers/kim2025_gammatune.pdf` 读取第一页确认：真实作者是 **Aayush Gautam, Susav Shrestha, Narasimha Reddy**（Texas A&M ECE），arXiv:2504.00030。计划正文（P5.0、附录A.2、附录E）里写的"Kim et al. 2025"是错的，全文没有姓 Kim 的作者。这条错误违反了计划自己在 §9.6"研究诚信"里定的规矩，需要在下一次改稿时统一订正为 "Gautam et al. 2025"。

## 3. 战略结论：大方向要不要改

**用户的目标是投 SWE / Agent 交叉岗位，不是发论文。** 在这个前提下，上面的重叠核查改变的是"怎么讲这个项目"，不是"项目本身有没有价值"：

- 如果卖点是"我发现了一个没人研究过的问题"——这个卖点站不住，QSpec/SpecKV/Nightjar 三篇论文基本上把支柱4/5 想讲的故事都讲过一遍了，面试官如果读过这几篇（大概率会读，因为项目自己引用了 SpecKV 和 Nightjar），"没人测过"这句话会被直接戳破。
- 如果卖点是"我能把这些独立的技术点（正确性验证的手写实现、量化、自适应控制）装配成一个能跑的本地 agent 推理加速系统，并且诚实记录了每一步的失效边界"——这个卖点是站得住的，且更贴近 SWE/Agent 岗位实际考察的能力（系统集成、调试真实平台约束、生产化判断），不需要跟已发表论文比新颖度。

**建议的具体调整方向**（下次改稿时执行）：

1. 全篇收紧"填补空白""调库拿不到"这类研究贡献措辞，改成"复现/对比 XX 论文的方法，验证在我自己的约束（Mac、单机、AWQ specifically）下是否成立"。
2. 支柱5/P5.3 明确改写为"参考 Nightjar 的熔断+重探测思路，用更轻量的周期性定时器代替它的 MAB 规划器，验证简化版本能否达到类似效果"——诚实定位为工程简化，而不是原创设计。
3. 更贴近 Agent 岗位的部分目前偏薄，值得加重：现在的 AgentBench-OS 验证是离线跑分（15-20个任务，测接受率），没有一个能实际接进 agent 循环里被调用的服务接口。建议补一个最小可用的本地推理服务封装（哪怕只是一个简单的 HTTP/CLI 层），跑一个"多轮工具调用的 agent 任务，用加速后端 vs 基线对比端到端延迟"的演示——这比接受率表格更容易让 Agent 团队的面试官直接理解"这个东西解决了我的什么问题"。
4. 保留：手写实现+逐token正确性证明、AWQ量化实现、诚实的失效边界记录（12个坑、8个拒绝方案）——这些是无论有没有人研究过都成立的工程判断力证据，是项目里最该保留的部分。
5. GammaTune 的定位从"贴近前沿的自适应算法"改成"一个简单、可解释、训练-free 的基线选择，写清楚为什么在预算约束下选它而不是 RL-based 方法"——诚实边界优于假装前沿，这也是计划自己 §4 的指导原则。
