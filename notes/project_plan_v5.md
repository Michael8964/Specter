## 1. 摘要

Specter 是一个面向 Agent 场景的本地推理加速引擎：手写实现投机解码（含严格的正确性证明/验证）和 AWQ 风格量化（含诚实的 kernel 说明），并用一套系统原理（内存带宽优化 vs 计算瓶颈的切换点）把两者统一起来，加上一个训练-free 的自适应投机步长控制器。目标硬件是个人 24GB 统一内存 Mac（开发/调试，$0）+ 短期云端 GPU 租用（规模化验证，$30-50）。当前状态：计划已经过两轮论文精读、一轮生产实践调研、一轮针对性踩坑调研，尚未开始任何代码实现。

---

## 2. 背景与问题陈述

现状：投机解码和量化在 2025-2026 已经是主流推理框架的标配（vLLM/SGLang/TensorRT-LLM 一个 flag 就能开），这意味着"会调库"本身已经没有技术含量。缺口在于：几乎没有人系统性地验证过——(a) 手写实现能否达到和调库一致的正确性保证，(b) 这些技巧在什么条件下会失效（batch size、压缩程度），(c) 主流生产库还没内置的"自适应控制"能做到什么程度。这个项目要填的就是这个"调库拿不到"的部分。

项目动机：现有简历（Time x Mart 市场撮合、TNT Carp Fishing 电商全栈）偏后端/全栈，缺少 AI/系统层面的深度项目，目标是在 2026 届新grad SWE市场里体现"工作2-3年才有的深度"，而不是新grad常见的"调一次现成API"级别项目。

## 3. 目标与非目标

### 目标
1. 手写实现投机解码的核心采样算法（rejection sampling），贪心模式下逐 token 精确验证正确性，采样模式下统计层面验证分布等价。
2. 手写实现 AWQ 风格的激活感知量化校准，并诚实区分"自己写的算法"和"复用的现成 kernel"。
3. 用一套统一的系统原理（内存带宽 vs 计算瓶颈）同时解释投机解码和量化各自的失效边界,并用真实 batch size 扫描实验测出具体的交叉点。
4. 实现一个训练-free 的自适应投机步长控制器,并验证它在压缩模型和真实生产基线（HF Transformers 内置动态投机）面前的表现。
5. 用 AgentBench 方法论改编的 agent 工具调用评测集,验证结构化输出场景下投机解码的优势。

### 非目标（显式声明,防止范围蔓延）
1. **不重新实现 GPTQ**——太复杂(基于二阶Hessian信息的逐层重构),用 LLM Compressor 做对比基线,不追求自己实现。
2. **不做完整 AgentBench 八个环境**——只改编 OS/bash 子环境,DB/知识图谱等环境对时间线来说太重。
3. **不重新实现 BanditSpec 的 bandit 理论方法或 AdaEDL 的熵基提前停止**——只作为文献对比引用,不追求代码复现,避免陷入证明 regret bound 之类的理论深坑。
4. **不训练专用 speculative head（EAGLE/Medusa 那种）**——没有多卡训练资源和预算,选经典两模型方案是预算约束下的合理取舍,不是不知道更优方案存在。
5. **不追求在 Mac 上跑出真实速度数字**——Mac 阶段只产出正确性/压缩率数字,真实速度数字明确留给云端阶段。
6. **不做多租户/高并发服务化**——项目关注单用户/低 batch 的本地 agent 场景,不做完整的生产级服务系统(不重新实现调度器、多租户隔离等)。

---

## 4. 指导原则（Tenets）

1. **能在免费环境验证的,绝不烧云端预算**——决定了"Mac 做正确性/算法验证,云端只做规模化速度验证"这条主线分工。
2. **诚实边界优于假装SOTA**——报告里明确写清楚"生产界最优解是什么、我们为什么没选它",这条原则贯穿方案选择的每一处(经典两模型方案、AWQ而非GPTQ自研、EMA控制器而非bandit理论)。
3. **正确性验证要有可复现的数学/统计依据,不能只看"结果看起来对"**——决定了贪心用逐token精确比对、采样用统计检验+任务指标的双重验证方法论,而不是主观判断。
4. **每个技巧不仅要证明"有效",还要测出"什么时候失效"**——决定了batch size交叉点实验和量化-步长耦合实验的存在,这是把项目从"实现了几个技巧"提升为"理解了系统边界"的核心原则。

## 5. 成功指标

| 指标 | 目标值 | 对应支柱 |
|---|---|---|
| 贪心模式输出与目标模型直接推理的 token 级一致性 | 100%(或仅有可忽略的浮点误差) | 支柱1 |
| 采样模式接受率 α 实测值与理论公式 $E[\min(p,q)]$ 的偏差 | 在统计显著性范围内吻合 | 支柱1 |
| 采样模式下游任务指标差距(HumanEval pass@1 / ROUGE) | <2 个点 | 支柱1 |
| 4-bit 量化后显存降低 | ~70% | 支柱2 |

| Batch size 交叉点实测 | 明确找到从正提升转向零/负提升的具体 batch 值,并与 Nightjar 的 30.25% 量级做对比 | 支柱4 |

## 6. 现有方案与文献综述

详见 [prior_art.md](prior_art.md)（生产实践/工程博客/开源实现）和 [papers/README.md](../papers/README.md)（17篇 arXiv 论文索引）。核心结论摘要：
- 投机解码/量化已是主流框架标配(vLLM/SGLang一个flag开启),真正的区分度在手写实现+正确性验证+边界刻画。
- IBM/PyTorch 生产复盘证实:代码/结构化输出场景投机解码效果最好,batch>64开始吞吐下降。
- AWQ 相对 GPTQ 对校准集分布更鲁棒(跨领域时 perplexity 涨幅相差近一个数量级)。
- 2024-2026 自适应投机控制是活跃前沿方向,且动态γ调整已是HF Transformers默认行为(4.45.0起),不是纯学术玩具。

## 7. 提议的方案与架构

### 五大支柱
1. 手写投机解码 + 正确性验证(贪心逐token比对 + 采样统计/任务指标验证,前置 α-gate)
2. AWQ 风格量化 + 诚实的 kernel 说明(自研校准算法,拆分为 Mac 正确性验证 + 云端速度对比两阶段)
3. AgentBench-OS 子环境评测
4. Batch size 交叉点实验(投机解码和量化分别扫描,统一系统原理解释)
5. 训练-free 自适应投机步长控制器(GammaTune算法,batch-aware熔断器,与支柱2的量化模型联动)

### 架构(v4 定稿)
```
Mac 开发阶段（阶段 0-4, $0）
  HF Transformers (PyTorch, MPS backend)
  ├─ 手写投机解码验证层（支柱1）
  ├─ 手写 AWQ 校准层（支柱2 上半,仅正确性/压缩率)
  ├─ AgentBench-OS 子集评测（支柱3）
  └─ GammaTune 风格自适应控制器（支柱5）
  交叉验证：mlx-lm 跑同一模型对做 α 数量级 sanity check

云端 GPU 阶段（阶段 5-6, $30-50）
  vLLM (生产实现对比基线) + LLM Compressor (GPTQ基线对比)
  ├─ 支柱2 下半：真实量化加速比 + LLM Compressor 对比
  ├─ 支柱4：batch size 交叉点扫描(大模型规模验证)
  └─ 支柱5 延伸：量化后最优 γ 偏移验证
```

详细坑位映射见第9节。

## 8. 考虑过的其他方案（新增章节）

| 决策点 | 选择的方案 | 考虑过的替代方案 | 拒绝理由 |
|---|---|---|---|
| 投机解码架构 | 经典独立草稿模型(两模型方案) | 训练专用 speculative head(EAGLE/Medusa 那种,IBM生产实测效果更好) | 需要多卡训练资源(IBM用PyTorch FSDP两阶段训练),个人项目没有这个预算;经典方案是可行性更高的合理取舍 |
| 量化方案自研对象 | AWQ(激活感知逐通道缩放) | GPTQ(基于Hessian的逐层重构) | GPTQ 实现复杂度(Cholesky分解等)和项目时间线不匹配;AWQ 对校准集分布更鲁棒,更适合作为"自己讲得清楚原理"的实现对象 |
| 量化对比基线工具 | LLM Compressor(vLLM团队统一工具) | 分别装 AutoGPTQ + AutoAWQ | 行业已经在从分裂工具链转向统一工具,用 LLM Compressor 更贴近当前生产标准;且两者在 Mac 上都不可用,不存在"Mac上先跑通AutoAWQ"这个中间态 |
| Mac 开发阶段主框架 | HF Transformers(PyTorch, MPS backend) | (a) vLLM CPU模式 (b) vLLM-metal插件 (c) MLX/mlx-lm 作为主实现 | (a) 实测比 llama.cpp 慢20-30倍,速度不可用;(b) 2026年仍是早期版本,模型覆盖不全;(c) MLX虽然性能更好且有社区先例,但 HF Transformers 有更直接的论文先例(SpecKV方法论原文如此),且更贴近简历读者熟悉的生态——MLX 降级为"交叉验证工具"而非主实现 |
| Agent 评测范围 | AgentBench 的 OS/bash 子环境 | 完整 AgentBench 八个环境(含DB、知识图谱等) | 完整八个环境对时间线太重;OS子环境的工具调用/结构化输出场景恰好是投机解码效果最好的场景,选它不只是"图省事",也是让支柱1效果最好看的场景 |
| 支柱5 控制器算法 | GammaTune(EMA更新,训练free) | (a) BanditSpec(UCB/EXP3老虎机,有理论遗憾界) (b) AdaEDL(基于熵的提前停止) | (a) 需要完整实现+调试bandit框架并处理遗憾界分析,时间成本和收益不成比例;(b) 是一种互补的"提前停止"思路而非"步长选择"思路,和GammaTune的问题设定不完全一致;两者都保留为文献对比对象,不重新实现 |
| 验证正确性的标准 | 贪心=逐token严格比对,采样=统计检验+任务指标 | 对采样模式也要求KL散度严格为0 | 不同设备/框架间不保证bit-exact输出(生产界共识),严格要求KL=0在工程上不现实且没有必要——只要统计层面的α和下游任务指标吻合,就已经验证了分布等价的核心保证 |

## 9. 已知风险与应对

### 9.1 平台兼容性硬约束（决定了整个方案的分阶段结构，不是普通的"坑"）

**风险 A：vLLM 在 Mac 上不能用（v3 架构图的前提是错的）**

调研结果（2025-2026 现状）：
- vLLM 默认安装要求 CUDA，Mac 上 `pip install vllm` 直接报 `Cannot find CUDA_HOME`。
- 即使用 `VLLM_TARGET_DEVICE=cpu` 强制装上 CPU 版本，实测性能是 **M5 Max 上 3-5 tokens/s**（Llama-3.1-8B, batch=4），对比 llama.cpp 用 Metal 跑同样模型是 **92 tokens/s**——差距 20-30 倍，这个速度不可能用来做任何有意义的投机解码/量化 benchmark。
- 官方在 2026 年推出的 `vllm-metal` 插件（用 MLX 做后端）才是真正的 GPU 加速路径，但截至目前仍是早期版本（v0.1→v0.2），要求原生 arm64 Python 3.12，模型覆盖不全，MoE 类模型基本跑不了，不适合作为一个有时间压力的个人项目的地基。
- 来源：[vLLM Issue #1441](https://github.com/vllm-project/vllm/issues/1441)、[vllm-metal GitHub](https://github.com/vllm-project/vllm-metal)、[Docker Model Runner 博客](https://www.docker.com/blog/docker-model-runner-vllm-metal-macos/)、[Contra Collective 2026 现状评测](https://contracollective.com/blog/vllm-mlx-apple-silicon-integration-2026)

**应对**：Mac 开发阶段（阶段0-4）不碰 vLLM，手写投机解码的验证/采样逻辑直接建在 HuggingFace Transformers + PyTorch（MPS backend）之上——这不是退而求其次，而是有论文先例：SpecKV 论文（2605.02888）方法论原文就是"We implement a manual speculative decoding loop using HuggingFace Transformers"。KV cache 自己用最简单的 dict/tensor 管理（这个阶段只需要单请求/小 batch，PagedAttention 解决的是多租户内存碎片问题，用不上）。云端阶段（阶段5-6）才引入 vLLM 做"生产级实现 vs 我们手写实现"的对比基线。

**风险 B：AutoAWQ / AutoGPTQ / LLM Compressor 全部要求 CUDA**

调研结果：
- **AutoAWQ**：官方要求 "NVIDIA GPU Compute Capability ≥ 7.5, CUDA ≥ 11.8"，无 Apple Silicon 支持。
- **AutoGPTQ**：维护者在 issue 里明确说需要专门写 MPS 版本的 C++ kernel 才能支持 macOS，目前没人做，纯 CUDA-only。
- **bitsandbytes**：历史上完全不支持 Mac，最近版本加了"实验性"Apple Silicon 支持，但不稳定，不能作为基线依赖。
- **LLM Compressor**（vLLM 团队做的统一量化工具，我们选它做对比基线）：底层依赖和 vLLM 生态一致，同样是 CUDA-first 设计，Mac 上无法产出有意义的速度数字。
- 来源：[AutoGPTQ Issue #223](https://github.com/PanQiWei/AutoGPTQ/issues/223)、[bitsandbytes Issue #252](https://github.com/bitsandbytes-foundation/bitsandbytes/issues/252)、[AutoAWQ PyPI 依赖说明](https://pypi.org/project/autoawq/0.2.0)

**应对**：把支柱2拆成两半——Mac 阶段（阶段2a）只做 AWQ 校准算法本身（纯矩阵运算，和 CUDA kernel 无关），产出压缩率和正确性指标（perplexity 差异、逐层量化误差分布），这些指标和硬件无关；云端阶段（阶段6）才用 LLM Compressor 跑 GPTQ 基线对比、测真实速度提升。报告里明确写清楚"为什么压缩率/正确性和实际加速比是两件独立的事，为什么必须分别在不同硬件上验证"。

**参照系：MLX 生态的经验阈值**

MLX 社区已有相对成熟的投机解码实现（`mlx-community/speculative-decoding`、`dflash-mlx`、`mlx-lm` 的 EAGLE-3 原型），其文档给出的实践经验：**接受率 α > 0.65 才有净加速**，低于这个阈值投机解码的草稿开销会抵消收益。这比"α < 0.4 是死亡区间下限"更保守也更具体。**应对**：阶段0的 α-gate 改成两级判断——α < 0.4 直接换模型对；0.4 ≤ α < 0.65 可以继续实现但要在报告里明确标注"理论上正确但实际加速可能有限"；α ≥ 0.65 才是"预期会有干净正向结果"的区间。MLX 本身不作为主实现框架，只在阶段0用来做一次交叉验证（同一模型对测出的 α 数量级是否和 HF Transformers 版本一致，几乎零成本的 sanity check）。

### 9.2 支柱1：手写投机解码 + 正确性验证

**坑1：草稿模型和目标模型的 tokenizer/vocab 不一致会让接受率静默归零**
现象：vocab 不匹配时投机解码不会报错，只会让接受率悄悄跌到接近 0，比基线还慢，且没有任何明显的错误信号提示你去查 tokenizer。更隐蔽的是同一个模型家族内部也可能不一致：Qwen2 1.5B 的 `vocab_size=151936`，72B 版本是 `152064`（padding token 导致的差异）。
**应对**：阶段0的 gate 检查清单里显式加一条——`assert draft_tokenizer.get_vocab() == target_tokenizer.get_vocab()`，选定具体模型尺寸后第一件事就跑这行断言，而不是等接受率异常了才回头查。

**坑2：bonus token 采样源搞错（真实存在的已知 bug 类型）**
现象：有实现（DSD）曾经错误地从**草稿模型**的分布采样 bonus token，而不是**目标模型**的分布，直接违反了投机解码"输出分布与目标模型完全一致"的核心正确性保证——而且这种 bug 不会崩溃，只会让"正确性验证"看起来通过了。
**应对**：写单元测试专门检查 bonus token 的采样代码路径来自哪个模型的 logits，而不是只看整体输出是否"看起来正常"。

**坑3：batch > 1 时的 ragged tensor 同步问题**
现象：不同序列在同一个 batch 里接受的草稿 token 数量不同，导致 position id、attention mask、KV cache 长度在 batch 内变得参差不齐（ragged），框架自动计算的 position id 在这种情况下可能产生错误值。
**应对**：支柱1阶段（默认 batch=1）可以先不管，但会在支柱4（batch 扫描实验）复活——提前在支柱4的设计里写清楚"batch > 1 时需要手动维护 per-sequence 的 position id 和 KV cache 长度，不能依赖框架的自动 padding 逻辑"，避免把这个同步 bug 误判成真实的计算瓶颈现象。

**坑4：draft/target 尺寸"死亡区间"**
EAGLE 论文明确警告过、IBM/PyTorch 生产博客也独立证实：两个模型尺寸差距不够大（比如只差2-3倍），投机解码可能比不用还慢，因为草稿模型本身的推理开销抵消了省下来的目标模型前向次数。诊断标准：如果 α 尚可（>0.5）但整体墙钟时间反而变慢，第一时间去查草稿模型自身的推理延迟占比，而不是怀疑验证逻辑写错了。

### 9.3 支柱2：AWQ 量化

**坑5：校准集分布和评测分布不一致会让 GPTQ 类方法严重过拟合，AWQ 相对稳健**
具体数字（AWQ 论文自己的实验）：校准集和评测集同分布时（PubMed→PubMed）两种方法都好；跨分布时（PubMed→Enron）AWQ 的 perplexity 只涨 0.5-0.6，GPTQ 涨 2.3-4.9——差了近一个数量级。
**应对**：设计一个小型交叉验证实验——用两个分布差异明显的校准集（比如代码语料 vs 自然语言语料）分别校准，再在两种评测集上分别测 perplexity，重现"同分布好、跨分布差"的矩阵。成本很低（复用已写好的校准 pipeline，只是换数据集跑几次），但能让报告从"实现了 AWQ"升级为"验证了 AWQ 相对 GPTQ 的核心优势来源"。

**坑6：校准集太小会过拟合**
标准实践：GPTQ 常用 C4 数据集、group size 128；校准样本数量太少（几十条量级）容易过拟合到校准集本身的措辞/句式而不是模型的整体权重分布。
**应对**：明确记录用了多少条校准样本（建议 128-512 条），并做一个"校准集大小 vs 量化后 perplexity"的小规模消融。

### 9.4 支柱3：Agent workload 评测

沿用 v3 依据，未发现新坑：选 AgentBench 的 OS 子环境改编是因为 IBM/PyTorch 生产复盘发现代码/结构化输出场景下投机解码效果最好，llama.cpp 社区独立观察一致——选这个评测场景不只是叙事需要，也是能让支柱1的效果最好看的场景，报告里要明确点出"为什么选这个评测场景"。

### 9.5 支柱4：Batch Size 交叉点实验

**坑7：Nightjar 给出的极端实测数字**
高负载下投机解码相比不用投机解码（Vanilla Decoding）吞吐反而下降最多 **30.25%**，且这个现象是在 vLLM 实际生产配置（ShareGPT 数据集、真实 QPS 曲线）下测出来的，不是理论推演——比"IBM/PyTorch batch>64 开始下降"这个表述更具体、更极端。
**应对**：报告里明确对标 Nightjar 这个具体数字——"我们在自己的模型/硬件组合上是否也能测出类似量级的负向效果，还是我们的交叉点在更高/更低的 batch"。

**坑8：草稿模型权重和 KV cache 抢显存（独立于计算瓶颈之外的第二个原因）**
Nightjar 的分析：草稿模型的权重本身占用 GPU 显存，和 KV cache 抢空间——batch 越大，KV cache 需要的显存越多，留给草稿模型的空间就越紧张。这和我们自己在 24GB 统一内存 Mac 上开发时天然遇到的资源约束是同一个原理的缩影——报告里可以明确点出这个类比：Mac 上因内存有限被迫做的取舍（比如选多小的草稿模型），本质上和生产环境里"大 batch 下 KV cache 和草稿模型争内存"是同一个系统性权衡。
**应对**：支柱4的实验记录里，除了吞吐提升比例，额外记录每个 batch size 下草稿模型权重和 KV cache 各自占用的显存量（哪怕只是估算）。

### 9.6 支柱5：自适应投机解码控制器

**坑9：GammaTune 自己承认的边界**
当 draft/target 组合本身就很匹配（接受率方差小）时，自适应 γ 的收益有限；且这个方法依赖历史接受率，在对抗性/剧烈波动的场景下会退化（GammaTune 论文 Limitations 章节原文）。
**应对**：不要只在一个"稳定"的 agent workload 上测 GammaTune 就下结论说"自适应有效"——故意设计一个接受率剧烈波动的测试场景（比如混合代码生成和开放式聊天的 prompt 序列，中途切换任务类型），验证 GammaTune 在这种场景下是否真的比固定 γ 更好，还是像论文承认的那样收益打折。

**坑10（本轮调研里价值最高的一条，把支柱2和支柱5绑在一起）：SpecKV 的量化-γ耦合发现**
SpecKV 核心论点：最优 γ 会随目标模型的量化程度系统性偏移，跨 FP16/INT8/NF4 三种压缩级别偏移幅度最高达 **41.2%**——量化和自适应 γ 控制不是两个独立技巧，量化本身就是一个会让固定 γ 失效的因素。
**应对**：直接复用支柱2已经做出来的量化模型（FP16 vs 我们自己 AWQ 量化后的4-bit版本），对同一个 draft/target 组合分别扫描最优 γ，验证"量化后最优 γ 是否发生偏移"。如果能测出类似 SpecKV 的偏移现象，这是一个用自己实现的两个组件（量化+投机解码）互相验证、而不是简单堆砌的实验，几乎不需要新写代码——只是把已有的两个组件用新方式组合起来跑。

**坑11：Nightjar 对现有自适应控制器工程缺陷的批评，直接决定我们熔断器该怎么设计**
Nightjar 点名批评了两个现有方法：(a) DSD（基于历史接受率）"一旦禁用投机解码，就不再收集新的观测数据，导致很难重新启用"（reactivation difficulty）；(b) BanditSpec"静态设计没有把实时 batch size 纳入决策上下文，也忽视了切换配置时 KV cache 重建的开销"。
**应对**：我们自己的"batch-aware 熔断器"（连接支柱4和支柱5）不能照抄简单的"batch 超过阈值就关闭投机解码"逻辑——(a) 熔断后必须保留一个低频率的周期性探测机制（比如每 N 步用很小的 γ 探一次实际接受率），否则 batch 降回低位后系统也没有信号知道该重新开启；(b) 如果实现了动态切换 γ/开关投机解码的逻辑，必须实测切换本身的开销（KV cache 是否需要重建、切换那一刻是否有延迟尖峰），不能假设切换是免费的。

**坑12：避免过度设计的范围声明**
BanditSpec 的方法论（UCB/EXP3 老虎机算法，带理论遗憾界证明）比 GammaTune 严谨得多，但实现和调试一个完整的 bandit 框架（尤其要复现它的 regret bound 分析）对时间线不现实。
**应对**：BanditSpec 和 AdaEDL 只作为文献对比对象引用（报告里讨论"和更理论化的 bandit 方法相比，我们选择的 EMA 方法在什么场景下够用、在什么场景下理论上有改进空间"），不重新实现——这个取舍和"GPTQ 不重新实现，只用 LLM Compressor 做对比"是同一种诚实的范围控制逻辑。

## 12. 验证/测试计划

- **贪心模式**：逐token严格比对,目标模型直接推理输出 vs 投机解码输出必须完全一致(或仅有可忽略浮点误差)。
- **采样模式**：(a) 统计层面验证实测α与理论公式 $E[\min(p,q)]$ 吻合;(b) 下游任务指标parity(HumanEval pass@1 或摘要ROUGE,差距<2点)。
- **量化正确性**：perplexity涨幅、逐层量化误差分布。
- **自适应控制器**：稳定场景+故意设计的波动场景(混合任务类型)双重测试,不只测理想情况。
- **交叉验证**：mlx-lm跑同一模型对,α数量级对拍;学习开源实现([romsto/Speculative-Decoding](https://github.com/romsto/Speculative-Decoding)等)做输出合理性sanity check。
