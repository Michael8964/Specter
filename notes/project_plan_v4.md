# Specter 项目计划 v4 —— 平台兼容性硬约束 + 全支柱踩坑预判

修订依据：v1（三支柱构想）→ v2（精读论文修正理论风险）→ v3（生产复盘，新增支柱4批大小交叉点）→ **v4（本版本）**：
1. 发现一个会让 v3 架构图直接跑不起来的硬约束（vLLM/AutoAWQ/AutoGPTQ/LLM Compressor 全部在 Mac 上不可用或性能崩溃），必须重排"哪个阶段用什么工具"。
2. 精读了自适应控制方向剩余 4 篇论文（SpecKV、AdaEDL、BanditSpec、Nightjar）的方法论和坑，加上针对性搜索"别人在实现投机解码/量化时踩过的具体坑"，把这些坑逐一映射回每个支柱，写成"已知坑 + 应对"小节，而不是等实现的时候自己撞上去。

---

## 一、核心定位（不变，来自 v3）

**Specter：面向 Agent 场景的本地推理加速引擎，附带正确性证明和边界条件的系统性刻画**

主线不变：投机解码和量化本质上都是"用空闲算力换内存带宽"，只在内存带宽瓶颈场景下有效，本项目要实测出各自失效的临界点。

---

## 二、平台兼容性硬约束（v4 新增，最重要的修订）

这一节是本次调研最大的发现——如果不处理，会在阶段 1-2 实现到一半才发现"根本跑不起来"，比 v3 里任何一个理论风险都更致命，因为它是**平台层面**的，不是"选错模型对"这种可以事后补救的问题。

### 1. vLLM 在 Mac 上不能用（v3 架构图的前提是错的）

调研结果（2025-2026 现状）：
- vLLM 默认安装要求 CUDA，Mac 上 `pip install vllm` 直接报 `Cannot find CUDA_HOME`。
- 即使用 `VLLM_TARGET_DEVICE=cpu` 强制装上 CPU 版本，实测性能是 **M5 Max 上 3-5 tokens/s**（Llama-3.1-8B, batch=4），对比 llama.cpp 用 Metal 跑同样模型是 **92 tokens/s**——差距 20-30 倍，这个速度不可能用来做任何有意义的投机解码/量化 benchmark。
- 官方在 2026 年推出的 `vllm-metal` 插件（用 MLX 做后端）才是真正的 GPU 加速路径，但截至目前仍是早期版本（v0.1→v0.2），要求原生 arm64 Python 3.12，模型覆盖不全，MoE 类模型基本跑不了，不适合作为一个有时间压力的个人项目的地基。
- 来源：[vLLM Issue #1441](https://github.com/vllm-project/vllm/issues/1441)、[vllm-metal GitHub](https://github.com/vllm-project/vllm-metal)、[Docker Model Runner 博客](https://www.docker.com/blog/docker-model-runner-vllm-metal-macos/)、[Contra Collective 2026 现状评测](https://contracollective.com/blog/vllm-mlx-apple-silicon-integration-2026)

**结论**：v3 架构图里"vLLM 的 KV Cache Manager/调度器不重造，自己的代码加在投机解码验证层和量化校准层"这句话，在 Mac 开发阶段**根本不成立**，因为 vLLM 在 Mac 上要么跑不动（CPU），要么不成熟（vllm-metal）。

**修订**：
- **Mac 开发阶段（阶段 0-3）**：不碰 vLLM。手写投机解码的验证/采样逻辑直接建在 **HuggingFace Transformers + PyTorch（MPS backend）** 之上——这不是退而求其次，而是有论文先例：SpecKV 论文（2605.02888）方法论原文就是"We implement a manual speculative decoding loop using HuggingFace Transformers"，说明这是学术界做正确性研究时的标准选择，不是因为没钱才将就。KV cache 自己用最简单的 dict/tensor 管理（反正只需要单请求、小 batch 的场景，PagedAttention 解决的是多租户内存碎片问题，我们这个阶段用不上）。
- **云端阶段（阶段 4-5）**：到了真正的 NVIDIA GPU 上，才引入 vLLM 做"生产级实现 vs 我们手写实现"的对比基线，这时候 `--speculative-config` 一行 flag 打开的 vLLM EAGLE/Medusa 支持才有意义——报告里可以明确写"我们的手写版本 vs vLLM 生产实现"的对比表，这本身就是一个有说服力的验证点（如果两者接受率/加速比数量级一致，说明手写实现是对的）。
- 架构图需要重画：Mac 阶段是"HF Transformers 手写 loop"，云端阶段是"vLLM 对比基线 + 大模型规模化验证"，两个阶段用的技术栈不同，这一点要在报告里诚实说明，而不是假装从头到尾都在同一套架构上做的。

### 2. AutoAWQ / AutoGPTQ / LLM Compressor 全部要求 CUDA

调研结果：
- **AutoAWQ**：官方要求 "NVIDIA GPU Compute Capability ≥ 7.5, CUDA ≥ 11.8"，无 Apple Silicon 支持。
- **AutoGPTQ**：维护者在 issue 里明确说需要专门写 MPS 版本的 C++ kernel 才能支持 macOS，目前没人做，纯 CUDA-only。
- **bitsandbytes**：历史上完全不支持 Mac，最近版本加了"实验性"Apple Silicon 支持，但不稳定，不能作为基线依赖。
- **LLM Compressor**（vLLM 团队做的统一量化工具，v3 里选它做对比基线）：底层依赖和 vLLM 生态一致，同样是 CUDA-first 设计，Mac 上无法产出有意义的速度数字。
- 来源：[AutoGPTQ Issue #223](https://github.com/PanQiWei/AutoGPTQ/issues/223)、[bitsandbytes Issue #252](https://github.com/bitsandbytes-foundation/bitsandbytes/issues/252)、[AutoAWQ PyPI 依赖说明](https://pypi.org/project/autoawq/0.2.0)

**结论**：v3 里"阶段2：AWQ 量化 + LLM Compressor 对比（Mac，$0）"这条时间线也站不住——LLM Compressor 在 Mac 上装不出速度数字。

**修订（把 Pillar 2 拆成两半，明确写清楚哪半在哪个阶段做）**：
- **Mac 阶段能做的**：AWQ 校准算法本身是纯矩阵运算（激活值统计 → 逐通道缩放因子 → 量化误差），跟 CUDA kernel 无关，可以用纯 PyTorch/NumPy 在 CPU/MPS 上实现和验证——产出的是**压缩率**（4-bit 后模型体积变化）和**正确性指标**（量化前后 perplexity 差异、逐层量化误差分布），这些指标和硬件无关，Mac 上跑出来的数字就是最终数字。
- **云端阶段才能做的**：LLM Compressor 跑 GPTQ 基线做对比、以及"量化后实际推理速度提升多少"——这两件事必须挪到阶段4-5（有真实 NVIDIA GPU 的时候）才做，Mac 阶段不要假装能测出速度数字。
- 这个拆分本身也是一个诚实、体现工程判断力的点：报告里可以专门写一段"为什么压缩率/正确性和实际加速比是两件独立的事，为什么必须分别在不同硬件上验证"——这比"糊里糊涂在 Mac 上跑出一个不可信的速度数字"要有说服力得多。

### 3. MLX 生态给了一个重要的参照系（不是必须用，但要知道存在)

调研发现 MLX 社区已经有相对成熟的投机解码实现（`mlx-community/speculative-decoding`、`dflash-mlx`、`mlx-lm` 里的 EAGLE-3 原型），其中一条经验值得直接借用：

> mlx-lm 文档给出的实践经验：**接受率 α > 0.65 才有净加速**，低于这个阈值投机解码的草稿开销会抵消掉收益。

这比 v3 里"α < 0.4 就不行"的门槛更保守也更具体——v3 的 0.4 是一个宽松的"死亡区间"下限，0.65 是"能不能实际提速"的更贴近生产的门槛。**修订**：阶段 0 的前置 gate 改成两级判断——α < 0.4 直接换模型对（v3 的判断不变），0.4 ≤ α < 0.65 可以继续实现但要在报告里明确标注"理论上有正确性但实际加速可能有限"，α ≥ 0.65 才是"预期会有干净的正向结果"的区间。

MLX 本身不作为项目的主实现框架（HF Transformers 更贴近简历读者熟悉的生态，且论文先例也用它），但可以在阶段0 用 `mlx-lm` 跑一次同样的模型对做交叉验证——如果 MLX 版本测出的 α 和我们自己 HF Transformers 版本测出的 α 数量级不一致，说明我们的实现可能有 bug，这是一个几乎零成本的 sanity check。

## 三、分支柱已知坑与应对（v4 新增核心内容）

### 支柱 1：手写投机解码 + 正确性验证

**坑 1：草稿模型和目标模型的 tokenizer/vocab 不一致会让接受率静默归零**
现象：vocab 不匹配时投机解码不会报错，只会让接受率悄悄跌到接近 0，比基线还慢，且没有任何明显的错误信号提示你去查 tokenizer——这是搜索中反复被提到的"最容易踩、最难发现"的坑。更隐蔽的是同一个模型家族内部也可能不一致：Qwen2 1.5B 的 `vocab_size=151936`，72B 版本是 `152064`（padding token 导致的差异）。
**应对**：阶段 0 的 gate 检查清单里显式加一条——`assert draft_tokenizer.get_vocab() == target_tokenizer.get_vocab()`，且要在选定 Qwen2.5 系列的具体两个尺寸之后，第一件事就是跑这行断言，而不是等接受率异常了才回头查。

**坑 2：bonus token 采样源搞错（真实存在的已知 bug 类型）**
现象：有实现（DSD）曾经错误地从**草稿模型**的分布采样 bonus token，而不是**目标模型**的分布，这直接违反了投机解码"输出分布与目标模型完全一致"的核心正确性保证——而且这种 bug 不会崩溃，只会让你的"正确性验证"看起来通过了（因为大部分 token 还是来自被接受的草稿或目标的修正），但统计意义上是错的。
**应对**：写单元测试专门检查 bonus token 的采样代码路径来自哪个模型的 logits，而不是只看整体输出是否"看起来正常"。

**坑 3：batch > 1 时的 ragged tensor 同步问题**
现象：不同序列在同一个 batch 里接受的草稿 token 数量不同，导致 position id、attention mask、KV cache 长度在 batch 内变得参差不齐（ragged），框架自动计算 position id 在这种情况下可能产生错误值。
**应对**：这个坑在支柱 1（默认 batch=1，贪心/采样验证）阶段可以先不管，但会在支柱 4（batch 扫描实验）复活——提前在支柱 4 的设计里写清楚"batch > 1 时需要手动维护 per-sequence 的 position id 和 KV cache 长度，不能依赖框架的自动 padding 逻辑"，避免到时候测出的"batch 大了变慢"其实是这个同步 bug 而不是真实的计算瓶颈现象。

**坑 4（沿用 v3，重新表述得更具体）：draft/target 尺寸比"死亡区间"**
EAGLE 论文明确警告过、IBM/PyTorch 生产博客也独立证实：两个模型尺寸差距不够大（比如只差 2-3 倍），投机解码可能比不用还慢，因为草稿模型本身的推理开销抵消了省下来的目标模型前向次数。阶段 0 的 α-gate 已经覆盖了这个问题的"效果"层面，但要额外记录一条**诊断标准**：如果 α 尚可（>0.5）但整体墙钟时间反而变慢，第一时间去查草稿模型自身的推理延迟占比，而不是怀疑验证逻辑写错了。

### 支柱 2：AWQ 量化

**坑 5：校准集分布和评测分布不一致会让 GPTQ 类方法严重过拟合，AWQ 相对稳健**
具体数字（AWQ 论文自己的实验）：校准集和评测集同分布时（PubMed→PubMed）两种方法都好；跨分布时（PubMed→Enron）AWQ 的 perplexity 只涨 0.5-0.6，GPTQ 涨 2.3-4.9——差了近一个数量级。
**应对**：不要只用一个校准集测一次就下结论。设计一个小型交叉验证实验——用两个分布差异明显的校准集（比如代码语料 vs 自然语言语料）分别校准，再在两种评测集上分别测 perplexity，重现"同分布好、跨分布差"的矩阵。这个实验成本很低（复用已经写好的校准 pipeline，只是换数据集跑几次），但能让报告从"实现了 AWQ"升级为"验证了 AWQ 相对 GPTQ 的核心优势来源"。

**坑 6：校准集太小会过拟合**
标准实践：GPTQ 常用 C4 数据集、group size 128；校准样本数量太少（几十条量级）容易过拟合到校准集本身的措辞/句式而不是模型的整体权重分布。
**应对**：明确记录用了多少条校准样本（建议 128-512 条，参考主流实践），并在报告里做一个"校准集大小 vs 量化后 perplexity"的小规模消融，用数据说话而不是抄一个默认值。

### 支柱 4：Batch Size 交叉点实验

**坑 7（用更强的数字替换 v3 里偏保守的表述）**：Nightjar 论文给出了比"IBM/PyTorch batch>64 开始下降"更极端的实测数字——**高负载下投机解码相比不用投机解码（Vanilla Decoding）吞吐反而下降最多 30.25%**，且这个现象是在 vLLM 实际生产配置（ShareGPT 数据集、真实 QPS 曲线）下测出来的，不是理论推演。
**应对**：v4 的支柱 4 实验设计不变（batch ∈ {1,4,8,16,32,64} 扫描），但报告里明确对标 Nightjar 这个具体数字——"我们在自己的模型/硬件组合上是否也能测出类似量级的负向效果，还是我们的交叉点在更高/更低的 batch"，这比单纯复现一条曲线更有讨论深度。

**坑 8（新发现，来自 Nightjar 对 KV cache 和显存竞争的分析）**：草稿模型的权重本身会占用 GPU 显存，和 KV cache 抢空间——batch 越大，KV cache 需要的显存越多，留给草稿模型的空间就越紧张，这是一个**独立于计算瓶颈之外的第二个"batch 越大越不划算"的原因**（不只是计算瓶颈,还有内存容量竞争）。这个现象和我们自己在 24GB 统一内存 Mac 上开发时天然会遇到的资源约束是同一个原理的缩影——**这是一个可以在报告里明确点出来的类比**：我们在 Mac 上因为内存有限而被迫做的取舍（比如选多小的草稿模型），本质上和生产环境里"大 batch 下 KV cache 和草稿模型争内存"是同一个系统性权衡，不是巧合。
**应对**：在支柱 4 的实验记录里，除了吞吐提升比例，额外记录每个 batch size 下草稿模型权重和 KV cache 各自占用的显存量，哪怕只是估算，也能让这张"含金量最高的图"多一个维度。

### 支柱 5（沿用上一轮提议，现在正式定稿）：自适应投机解码控制器

**核心设计不变**：基于 GammaTune 的 Algorithm 1（训练free、EMA 更新 γ）实现，用 HF Transformers 默认的动态投机解码（v4.45.0 起自带）作为生产基线对比。

**坑 9（GammaTune 自己在 Limitations 里承认的边界，v3 已记录，这里强调"应对"而不只是"记录"）**：当 draft/target 组合本身就很匹配（接受率方差小）时，自适应 γ 的收益有限；而且这个方法依赖历史接受率，在对抗性/剧烈波动的场景下会退化。
**应对**：不要只在一个"稳定"的 agent workload 上测 GammaTune 的收益就下结论说"自适应有效"——故意设计一个接受率剧烈波动的测试场景（比如混合代码生成和开放式聊天的 prompt 序列，中途切换任务类型），验证 GammaTune 在这种场景下是否真的比固定 γ 更好，还是像论文承认的那样收益打折。这比只测"理想场景"更能体现你理解这个方法的边界。

**坑 10（新发现，来自 SpecKV，也是本轮调研里最有价值的一条，因为它直接把支柱 2 和支柱 5 绑在一起）**：SpecKV 的核心论点是**"最优 γ 会随目标模型的量化程度系统性偏移，跨 FP16/INT8/NF4 三种压缩级别偏移幅度最高达 41.2%"**——也就是说,量化和自适应 γ 控制不是两个独立的技巧,量化本身就是一个会让固定 γ 失效的因素。
**应对（升级支柱 5 的实验设计）**：不要只在 FP16 目标模型上测 GammaTune,而是直接复用支柱 2 已经做出来的量化模型（FP16 vs 我们自己 AWQ 量化后的 4-bit 版本），对同一个 draft/target 组合分别扫描最优 γ，验证"量化后最优 γ 是否发生偏移"。如果能测出类似 SpecKV 的偏移现象,这是一个**用自己实现的两个组件（量化+投机解码）互相验证、而不是简单堆砌**的实验,是全项目里除了支柱4之外含金量第二高的加分点,而且几乎不需要新写代码——只是把已有的两个组件用一种新的方式组合起来跑。

**坑 11（新发现，来自 Nightjar 对现有工作的批评，直接决定我们自己的"熔断器"该怎么设计）**：Nightjar 论文点名批评了两个现有方法的具体工程缺陷——
1. DSD（基于历史接受率的方法）"一旦禁用投机解码，就不再收集新的观测数据，导致很难重新启用"（reactivation difficulty）。
2. BanditSpec"静态设计没有把实时 batch size 纳入决策上下文，也忽视了切换配置时 KV cache 重建的开销"。
**应对**：这两条直接决定了我们自己"batch-aware 熔断器"（连接支柱4和支柱5的设计）该怎么写，不能照抄一个简单的"batch 超过阈值就关闭投机解码"逻辑：
- 熔断后必须保留一个**低频率的周期性探测机制**（比如每 N 步用很小的 γ 探一次实际接受率），否则一旦 batch 降回低位，系统也没有信号知道该重新开启——这是直接吸取 DSD 的教训。
- 如果实现了"动态切换 γ/开关投机解码"的逻辑，必须**实测切换本身的开销**（比如 KV cache 是否需要重建、切换那一刻是否有延迟尖峰），而不是假设切换是免费的——这是直接吸取 BanditSpec 被批评的教训，也是一个可以在报告里明确写"我们测过切换开销，证明不是免费的/是可以忽略的"这种诚实细节的地方。

**坑 12（决定实现范围，避免过度设计）**：BanditSpec 的方法论（UCB/EXP3 老虎机算法，带理论遗憾界证明）比 GammaTune 严谨得多，但实现和调试一个完整的 bandit 框架（尤其是要复现它的 regret bound 分析）对时间线来说不现实。
**应对（明确写进范围声明）**：BanditSpec 和 AdaEDL 只作为**文献对比对象**引用（报告里讨论"和更理论化的 bandit 方法相比,我们选择的 EMA 方法在什么场景下够用、在什么场景下理论上有改进空间"），不重新实现。这个取舍和 v3 里"GPTQ 不重新实现,只用 LLM Compressor 做对比"是同一种诚实的范围控制逻辑,应该在报告里用同一套语言写清楚。

## 六、简历 bullet 草稿（v4 更新）

- 手写实现投机解码采样算法，贪心模式下逐 token 精确验证正确性，采样模式下通过统计检验和任务指标 parity 确认分布等价；诊断并规避 tokenizer 不一致、bonus token 误采样等已知实现陷阱

- **实测投机解码与量化在不同 batch size 下的吞吐增益曲线，定位出两者从"内存带宽优化"转为"计算瓶颈拖累"的交叉点**，并验证量化程度对最优投机解码步长的系统性影响（复现/扩展 2026 年最新研究 SpecKV 的核心发现）
- 实现训练-free 的自适应投机解码步长控制器（基于 EMA 的 GammaTune 算法），设计 batch-aware 熔断与周期性重探测机制，对标 Hugging Face Transformers 内置动态投机解码基线
- 基于 AgentBench 方法论改编 agent 工具调用评测集，验证结构化输出场景下投机解码接受率显著高于自由文本生成

## 七、结论

v4 在 v3 的基础上做了两类修订：
1. **平台兼容性硬约束**——发现 vLLM/AutoAWQ/AutoGPTQ/LLM Compressor 在 Mac 上全部不可用或性能崩溃，重新设计了"Mac 阶段做什么、云端阶段做什么"的分工，避免实现到一半才发现跑不起来。
2. **12 个具体的已知坑**，逐一映射到 5 个支柱，每条都标注了来源（论文的 Limitations 章节、生产博客、GitHub issue）和具体的应对代码/实验设计，而不是泛泛地说"要注意鲁棒性"。

其中坑 10（SpecKV 的量化-γ耦合发现）和坑 11（Nightjar 对熔断器设计的批评）价值最高——前者把支柱2和支柱5从"两个独立技巧"变成"互相验证的一组实验"，后者直接决定了我们自己的核心创新点（batch-aware 熔断器）该怎么设计才不重蹈别人的覆辙。

这是目前评估下经过最彻底踩坑预判的一版计划。时间线从 v3 的 19-23 天延长到 24-27 天，预算从 $25-45 涨到 $30-50——这个涨幅主要来自平台兼容性问题带来的阶段拆分（阶段2 拆成 Mac/云端两半）和支柱5的完整加入，不是范围蔓延。
