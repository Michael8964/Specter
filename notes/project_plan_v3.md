# Specter 项目计划 v3 —— 论文 + 生产实践双重验证后的定稿

修订依据：v1（三大支柱构想）→ v2（精读论文原文后修正三处理论风险）→ v3（本版本，基于 [prior_art.md](prior_art.md) 里的生产复盘，把项目从"两个独立技巧"提升为"一个系统原理的两个例证"）。

## 一、核心定位（不变）

**Specter：面向 Agent 场景的本地推理加速引擎，附带正确性证明和边界条件的系统性刻画**

新增一句话主线：投机解码和量化本质上都是"用空闲算力换内存带宽"，只在内存带宽瓶颈（低 batch/单用户延迟）场景下有效——本项目不仅要证明"能加速"，还要**实测出它们各自失效的临界点**。这条主线把三大支柱串成一个整体论述，而不是三个不相关的实验。

## 二、四大支柱（新增一个）

### 支柱 1：手写投机解码 + 正确性验证（沿用 v2，细化验证流程）
- 贪心模式：逐 token 严格比对（生产界共识——这是唯一能做 bit-level 比较的设置，来源：llama.cpp 文档、PyTorch/IBM 博客均建议"exact matching 用 greedy"）
- 采样模式：统计层面验证 α 实测值 vs 理论公式 $\alpha=E[\min(p,q)]$，加任务指标 parity（HumanEval pass@1 或摘要 ROUGE，目标差距 <2 点，对标 Chen et al. 论文 Table 1 的验证方式）
- **前置 gate（新增）**：正式实现投机解码主体之前，先花半天测 draft/target 候选组合的 α 值。α 明显偏低（<0.4，或者 draft 模型本身开销太大导致理论加速比 <1）就先换模型对，不要等实现完整个 pipeline 才发现选错了——这是 EAGLE 论文警告的"死亡区间"和一位实践者"测 τ=1.81 就预判掉速"经验的操作化。
- γ ∈ {1,3,5,7,10} 扫描（v2 已定）

### 支柱 2：AWQ 风格量化 + 诚实的 kernel 说明（沿用 v2）
- 自己实现激活感知逐通道缩放校准
- 对比基线工具从 AutoGPTQ/AutoAWQ **改为 LLM Compressor**（vLLM 团队做的统一量化工具，是当前生产标准，来源见 prior_art.md）
- 报告明确写清楚"哪部分是自己写的算法，哪部分复用现成 kernel"

### 支柱 3：Agent workload 评测（沿用 v2，补充选择依据）
- 只做 AgentBench 的 OS 子环境改编（Docker 沙箱 + bash 工具调用，15-20 个任务）
- **新增依据**：IBM/PyTorch 生产复盘发现代码/结构化输出场景下投机解码效果最好（代码模型能用 6-8 个 draft head，语言任务只能用 3-4 个），llama.cpp 社区独立观察一致。选 agent 工具调用场景不只是叙事需要，也是能让支柱 1 的效果最好看的场景——这一点要在报告里明确点出来，体现你知道"为什么选这个评测场景"而不是随便选的。

### 支柱 4（新增）：Batch Size 交叉点实验
- **动机**：三个独立生产来源都指向同一个现象——IBM/PyTorch 实测 batch>64 时投机解码开始吞吐下降；SGLang 团队发现 EAGLE 在 batch=24 就掉速（EAGLE-3 撑到 batch=64 还有 38% 提升）；AutoAWQ 官方文档承认高 batch 下量化因反量化开销可能比不量化还慢。三者说的是同一件事：内存带宽瓶颈 vs 计算瓶颈的切换点。
- **实验设计**：对投机解码和 AWQ 量化分别在 batch ∈ {1, 4, 8, 16, 32, 64} 下测吞吐提升比例，画出两条"提升比例 vs batch size"曲线，标出各自从正提升转向零/负提升的交叉点。
- **价值**：这是全项目里含金量最高的一张图——它不是简单复现别人的结论，而是在自己选定的模型/硬件组合上**实测出这个交叉点具体在哪**，并用一套系统原理同时解释两个看似独立的技巧为什么都有这个现象。面试时如果只能展示一张图，就是这张。

## 四、分阶段计划（19-23 天，比 v2 多 1 天用于支柱 4）

### 阶段 0：立项 + 存活性 gate（第 1-2 天，Mac，$0）

### 阶段 1：投机解码手写实现 + 双重验证（第 3-9 天，Mac，$0）
- 贪心严格比对 + 采样统计/任务指标验证
- γ 扫描

### 阶段 2：AWQ 量化 + LLM Compressor 对比（第 10-14 天，Mac，$0）
- 自研校准算法 + 逐层误差分析
- LLM Compressor 跑 GPTQ 基线做对比

### 阶段 3：AgentBench-OS 子集评测（第 15-17 天，Mac，$0）

### 阶段 4（新增内容）：Batch Size 交叉点实验（第 18-19 天，Mac 小模型 + 云端大模型，$10-20）

### 阶段 5：规模化验证（第 20-21 天，云端，$15-25）
- 34B 级别模型重跑核心投机解码+量化实验，产出最终对比表

### 阶段 6：产出（第 22-23 天，$0）

## 五、简历 bullet 草稿（v3 更新，新增交叉点实验的表述）

- 手写实现投机解码采样算法，贪心模式下逐 token 精确验证正确性，采样模式下通过统计检验和任务指标 parity 确认分布等价
- 自研 AWQ 风格激活感知量化校准 pipeline，4-bit 量化下显存降低 ~70%，perplexity 涨幅 <5%
- **实测投机解码与量化在不同 batch size 下的吞吐增益曲线，定位出两者从"内存带宽优化"转为"计算瓶颈拖累"的交叉点**，用统一的系统原理解释两种独立优化技巧的共同边界条件
- 基于 AgentBench 方法论改编 agent 工具调用评测集，验证结构化输出场景下投机解码接受率显著高于自由文本生成

## 六、结论

v3 在 v2 的基础上没有推翻任何结论，而是新增了一个由三个独立生产来源共同支撑的核心实验（支柱 4），把项目的叙事从"实现了两个论文里的技巧"提升为"发现/验证了一个连接两个技巧的系统原理"。这是目前评估下含金量最高的一版计划。下一步如果没有更多需要补充调研的方向，可以开始动手实现阶段 0。
