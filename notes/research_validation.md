# Specter 计划 vs 文献验证

基于 papers/ 里 12 篇论文，逐条核对原计划的技术假设，标出「成立」「需要调整」「过于乐观」。

## 支柱 1：手写投机解码 + 正确性验证

**成立，且比原计划设想的更严格。**
- Leviathan et al. (2211.17192) 和 Chen et al. (2302.01318) 都证明：只要 draft 和 target 模型的 logits 计算是精确的，modified rejection sampling 产生的输出分布与直接从 target 模型采样**完全相同（exact，不是近似）**。
- 调整点：原计划写的是"用 KL 散度检验证明分布一致"，这个说法要改成——**理论上 KL 散度应该严格为 0**（在 float 精度误差范围内，比如 1e-6 量级）。如果实测 KL 散度明显偏离 0，说明实现有 bug（比如温度处理错了、tie-breaking 没对齐），而不是"可以接受的近似"。这个更严格的说法在面试时更站得住脚，也更容易被追问出真才实学。
- 加分项：EAGLE (2401.15077) 指出用固定的小 draft 模型，接受率和加速比都不如"从 target 模型自身特征外推"的方法（EAGLE 系列做到 3–6.5x，比经典两模型投机解码的 2–3x 明显更高）。**建议**：主实现用经典两模型方案（可行性高、两周内能做完、正确性证明清晰），但在 README/报告里做一节"与 EAGLE/Medusa 的对比分析"，说明为什么选经典方案、SOTA 方法的 trade-off 是什么。这样即使没实现 EAGLE，也能展示你读懂了整个技术谱系，含金量不降反升。

## 支柱 2：量化 pipeline + 误差分析

**基本成立，需要明确选哪种量化方法作为"自己实现"的部分。**
- 三篇量化论文的方法论不同，复杂度差异很大：
  - **AWQ**（2306.00978）：只需要激活值的统计量（per-channel 幅值），做等价的逐通道缩放，数学上简单，一两天能撸完核心逻辑，适合"自己实现"。
  - **GPTQ**（2210.17323）：需要计算二阶 Hessian 近似并做逐层重构，数学和工程复杂度都高很多，一周内独立实现有较大风险。
  - **SmoothQuant**（2211.10438）：做的是 W8A8（权重+激活都量化），比纯权重量化多一层复杂度。
- **建议**：自己实现 AWQ 风格的 per-channel 激活感知量化（可行性最高），GPTQ/SmoothQuant 作为**对比基线**用现成实现（比如 AutoGPTQ、AutoAWQ 库）跑出数字，写清楚"重现了 AWQ 的核心思想，并与 GPTQ/SmoothQuant 的公开实现做了效果对比"。这比硬啃 GPTQ 的 Hessian 数学更符合两周时间预算，同时"自己实现+和 SOTA 库对比"的叙事本身就很有说服力。

## 支柱 3：Agent workload 评测

**成立，且原计划"自己设计 20-30 个任务"的说法应该改进。**
- AgentBench（2308.03688）和 ToolLLM（2307.16789）已经是标准化的 agent/工具调用评测方法论，各自有明确的任务结构和评分标准。
- **调整点**：不要完全"自己发明"评测集，而是**从 AgentBench 或 ToolLLM 的任务格式里挑一个子集/改编**，并注明"评测方法参考 AgentBench (Liu et al., ICLR'24)"。这样评测的可信度和可复现性大幅提升——招聘方/面试官一看就知道不是拍脑袋编的题目，而是对标了学术界认可的基准。

## 架构：造轮子 vs 用轮子

**原计划"复用 vLLM 底层组件"是对的，论文进一步明确了边界。**
- PagedAttention 论文（2309.06180）本身就是在解决 KV cache 碎片化和批处理效率问题，vLLM 相比 FasterTransformer/Orca 有 2-4x 吞吐提升——这套调度器工程量极大（原计划里也提到"不要重造"）。
- **结论不变**：KV cache 管理、continuous batching 直接用 vLLM 现成实现；你自己的代码只加在"投机解码验证层"和"量化校准层"，这两层是插在 vLLM 之上/之外的独立模块，不侵入它的调度核心。这样项目边界清晰，也方便在 README 里画清楚"哪些是我写的，哪些是复用的"。

## 需要补充到计划里的东西

1. **加速比的诚实基准**：文献里两模型投机解码的加速比是 2-3x（Leviathan/Chen），EAGLE 系列是 3-6.5x。原计划写的"2-3x"目标是合理的，但要注明这是**经典两模型方案**的量级，不要写成 EAGLE 级别的数字，否则被追问实现细节会露馅。
2. **接受率依赖 draft/target 相似度**：两篇奠基论文都强调 draft 模型的选择直接决定接受率。计划里应该加一步"draft/target 模型选型的消融实验"（比如同系列 1.5B vs 跨系列小模型的接受率对比），这本身就是一个不错的图表素材。
3. **数值精度陷阱**：投机解码的"分布不变"证明依赖精确的 softmax 概率比较，实际 GPU 上 fp16/bf16 的舍入误差可能导致极小概率偏差——这是文献没有细讲、但实现时一定会踩到的坑，值得在报告里专门写一节"数值精度对正确性验证的影响"，这种细节是简历上最能体现"深挖过"的地方。

## 结论

原计划的三大支柱和总体路线**成立**，论文验证后只需要做两处收缩（GPTQ 改用现成库做对比而非自己实现二阶重构、agent 评测对标 AgentBench/ToolLLM 而非完全自创），可行性和含金量都进一步提高。18-22 天的时间预算不需要调整。
