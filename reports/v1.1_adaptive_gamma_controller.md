# Specter — Milestone Report v1.1: Adaptive Speculation-Length Controller (GammaTune)

**Scope:** P5.0 – P5.1 (Track/Pillar 5)
**Status:** Complete, verified by direct execution (not by code review alone)
**Models used in this milestone:** draft = Qwen2.5-0.5B-Instruct, target = Qwen2.5-1.5B-Instruct (same temporary stand-in pair as v1.0)

## 1. Summary

This milestone implements GammaTune, an adaptive controller that adjusts the speculation length (gamma — how many candidate tokens the draft model proposes per round) in real time based on how often the draft model's recent guesses were accepted, instead of using one fixed gamma for an entire generation. The hypothesis: a fixed gamma wastes sequential draft-model compute whenever candidates get rejected early and under-uses the draft model when it's doing well, so a controller that expands gamma when things are going well and contracts it when they aren't should beat a well-chosen fixed gamma end-to-end.

The measured result does not fully support that hypothesis at the strength originally expected. The controller behaves exactly as designed — it reliably shrinks gamma during a hard/volatile phase and cuts draft-side compute substantially — but the end-to-end wall-clock speedup is modest (~8–9%), because the target model's per-round verification cost, which does not shrink with gamma, dominates round time. This milestone's most useful output is arguably not the speedup number itself but the diagnosis of *why* it's smaller than expected, which directly points to where the next real gains have to come from (see Section 6).

## 2. What was built

| Stage | Deliverable | Purpose |
|---|---|---|
| P5.0 | `src/gamma_tune.py` (`GammaTuneController`) | Algorithm 1: on full acceptance, probe upward un-smoothed (`gamma <- n_accepted + delta`); on any rejection, fall back via an EMA of the accepted count (`gamma_bar <- clip(gamma_min, gamma_max, (1-eta)*gamma_bar + eta*n_accepted)`, `gamma <- ceil(gamma_bar)`). "Expand fast, shrink smoothly." |
| P5.1 | `scripts/p5_gamma_tune_demo.py` | Qualitative check: does the controller's gamma trace actually expand/contract in a sensible way round to round, on real generations? |

| P5.1 | `scripts/p5_fluctuation_scenario.py` | A scenario built specifically to *not* be steady: an easy counting phase followed by an abrupt switch to open-ended creative writing, in one continuous generation — tests whether the adaptive controller's edge grows when difficulty changes mid-generation. |
| P5.1 | `scripts/p5_draft_target_split.py` | Diagnostic follow-up to explain the fluctuation-scenario result: times `draft_propose()` and `target_verify()` separately (instead of only total round time) to see where the time in a round is actually going. |

All three timed scripts reuse `draft_propose` / `target_verify` / `speculative_decoding_step` unmodified from the already-verified `src/speculative_decode.py` core (v1.0) — only the loop around them changes to consult `GammaTuneController` instead of a fixed gamma, or to add timing instrumentation. The P1 correctness guarantees (greedy equivalence, statistically-validated acceptance rate) are not re-derived here; this milestone assumes them and focuses on throughput.

## 3. Results

All numbers below are from actual runs (raw stdout logs saved alongside this report as `results/p5_*.log`; structured summaries as `results/p5_*_result.json`), 3 runs per configuration per the project's "don't trust a single run" standard.

### 3.1 Steady-prompt throughput (`p5_gamma_tune_speedup.py`)

| | Fixed gamma=5 | GammaTune adaptive |
|---|---|---|
| Throughput (tok/s, mean ± std, 3 runs) | 20.91 ± 1.44 | 22.72 ± 1.29 |

**Speedup (adaptive / fixed): 1.087x** (~8.7%).

### 3.2 Fluctuation scenario (`p5_fluctuation_scenario.py`)

| | Fixed gamma=5 | GammaTune adaptive |
|---|---|---|
| Phase 1 (easy, tok/s) | 23.33 ± 6.86 | 22.20 ± 4.86 |
| Phase 2 (hard, tok/s) | 10.61 ± 2.96 | 10.94 ± 0.93 |
| Total (tok/s) | 13.48 ± 1.44 | 14.58 ± 1.93 |
| Phase2/Phase1 ratio (how much throughput drops in the hard phase) | 0.455 | 0.493 |

**Overall speedup (adaptive / fixed, total throughput): 1.081x** (~8.1%) — essentially the same magnitude as the steady-prompt result, not larger.

**Caveat:** in phase 2, the fixed-vs-adaptive gap (10.94 − 10.61 = 0.33 tok/s) is smaller than either configuration's own standard deviation (2.96 and 0.93). At n_runs=3, "the adaptive controller has a bigger edge in the hard phase" is a weak, noisy signal here, not a confirmed effect — it would need more runs (or a larger, more controlled hard-phase benchmark) to say with confidence.

### 3.3 Draft-side vs. target-side time split (`p5_draft_target_split.py`)

Single isolated forward pass: draft = 21.5 ms, target = 53.6 ms → **c = T_target / T_draft = 2.49**.

Phase 2 (hard), 3 runs, mean ± std:

| | Fixed gamma=5 | GammaTune adaptive |
|---|---|---|
| Draft-side time (s) | 1.973 ± 0.322 | 1.226 ± 0.079 |
| Target-side time (s) | 1.084 ± 0.139 | 1.146 ± 0.037 |

**Draft-side time saved by adaptive: 37.8%.** **Target-side time change: −5.7%** (i.e. adaptive's target-side time was slightly *higher*, not flat — plausibly because the adaptive controller runs more, smaller rounds in the hard phase, each round paying the same roughly-fixed per-call target cost).

## 4. Interpretation

The controller is doing exactly what it was designed to do — Section 3.3 shows a real, large (37.8%) cut in draft-side compute during the hard phase, and the qualitative gamma trace (recorded in `p5_fluctuation_scenario.log`) shows gamma collapsing to 1 almost immediately after the phase transition and only occasionally probing upward, which is the intended "shrink smoothly, probe fast" behavior from Section 1's algorithm.

The reason this doesn't translate into a comparably large end-to-end speedup is that target-side time (~1.1s) is *larger* than the draft-side savings being fought over, and — critically — it does not decrease when gamma shrinks. A round's wall-clock cost is roughly `T_target_verify + gamma_used * T_draft_step`; shrinking gamma only ever attacks the second term, while the first term (dominated by one large-model forward pass per round, `c ≈ 2.5x` a single draft step) stays essentially constant per round. This is consistent with, and gives a mechanistic explanation for, the modest ~8–9% overall numbers in Sections 3.1–3.2: the theoretical ceiling on what gamma-tuning alone can achieve is capped by how much of total round time is attributable to gamma-dependent compute in the first place, and that fraction is smaller than initially assumed.

## 5. Honest caveats

- n_runs = 3 throughout; Section 3.2's hard-phase comparison in particular is within noise (see caveat there).
- All three scripts use the same single draft/target pair and short token budgets (30–40 tokens per phase) — this is a short-horizon result on one model pair, not yet shown to generalize to longer generations or other model sizes.
- The target-side time in Section 3.3 was expected to be flat and instead moved slightly against the adaptive controller. This is plausible (more, smaller rounds → more fixed per-call overhead paid more often) but not yet directly isolated or measured — it's a hypothesis for the next investigation, not a confirmed mechanism.

## 6. What's next

Per the project roadmap (Pillar 5), the literal next stage is P5.2 (quantization–gamma coupling), but that stage requires the AWQ-quantized model from Pillar 2 (not yet built) and cloud GPU time, so it's blocked for now.

The next stage that *can* be done locally, P5.3 (batch-aware circuit breaker), has a hard prerequisite that this milestone surfaced: P5.3 requires measuring real KV-cache rebuild/switching overhead, but the current `draft_propose` / `target_verify` implementation has **no incremental KV-cache at all** — every draft step and every target verification recomputes attention over the entire growing sequence from scratch. Section 4's cost model above (`T_target_verify` roughly constant per round) is itself inflated by this: a properly cached target forward pass would only need to attend over the *new* tokens each round, not re-derive the whole context every time. Adding real `past_key_values`-based incremental caching to both `draft_propose` and `target_verify` — with correct cache rollback on rejection — is therefore the next milestone (v1.2), both because P5.3 depends on it and because it will make Section 3–4's own numbers more representative of a real deployment.
