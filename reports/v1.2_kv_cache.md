# Specter — Milestone Report v1.2: Incremental KV-Cache for Speculative Decoding

**Scope:** P5.3 prerequisite (Track/Pillar 5)
**Status:** Complete, verified by direct execution, including a root-cause bug fix found mid-investigation, plus additional adversarial verification and a reproducibility re-check performed after the fix was committed (Section 3.5)
**Models used in this milestone:** draft = Qwen2.5-0.5B-Instruct, target = Qwen2.5-1.5B-Instruct (same pair as v1.0/v1.1)

## 1. Summary

v1.1 identified that `draft_propose`/`target_verify` (the v1.0 core) recompute attention over the *entire* growing sequence on every single call, with no cache at all — and flagged this as a hard blocker for P5.3, which requires measuring a real KV-cache rebuild/switching cost. This milestone adds an incremental, `past_key_values`-based cache (`src/speculative_decode_kv.py`) that reuses cached Key/Value tensors instead of recomputing them, with correct rollback when speculative candidates are rejected.

The investigation did not go in a straight line, and the crooked path is the most useful part of this report. The first working version passed every *greedy-mode* correctness check but was **slower** than the uncached baseline at short generation lengths, and only modestly faster (1.65x) at long ones. A deeper, harder-to-fool verification method — a synthetic model whose output depends only on absolute token position, with zero floating-point noise — proved that the sampling-mode mismatches we had earlier (incorrectly) diagnosed as "benign floating-point noise" were actually a real logic bug: the draft cache's rollback target was missing a term that the target cache's (correct) rollback already had, silently wiping the cached prompt on round 0 and making every subsequent draft proposal be computed from the wrong absolute position. Greedy-mode correctness never caught this, because a rejection always falls back to the (correctly cached) target model's own token regardless of what the mispositioned draft proposed. Fixing it raised the measured speedup at 400 tokens from **1.65x to 3.86x**.

After that fix was committed, the user reasonably asked for more testing before trusting the result, given that this same investigation had already produced one wrong diagnosis and two real sequential bugs. Section 3.5 covers the three additional checks run in response: a harder adversarial fake-model sweep, an EOS-mid-block truncation test, and a from-scratch reproducibility re-run of the speedup benchmark with a different random seed batch.

## 3. Results

### 3.1 The bug, and how it was found

`speculative_decoding_step_cached` rolls both caches back after each round to discard rejected candidates. The target cache's rollback target was `target_start_len + target_seed_ids.shape[1] + n_accepted` (correct). The draft cache's was `draft_start_len + n_accepted` — **missing the seed-length term**. On round 0 (`draft_start_len = 0`, a rejection so `n_accepted = 0`), this cropped the draft cache to length 0, discarding the just-cached prompt entirely. From round 1 onward, the draft model's `position_ids` were then computed from that wrong (too-small) cache length, so every later draft proposal was generated from the wrong absolute position in the sequence.

This was invisible to `p5_kv_cache_verify.py`'s greedy-mode check (9/9 pass, both before and after the fix) because greedy mode's output on any rejection is the target model's own greedy token — computed from the correctly-tracked target cache, independent of whatever the mispositioned draft actually proposed. The bug degraded the draft's real usefulness without ever producing a wrong *greedy* output token.

It was caught by `p5_kv_cache_fake_model_verify.py`: a synthetic model whose logits are a deterministic function of absolute position only (`sin`/`cos` of position and vocab index, no learned weights, no attention). `p5_kv_cache_fake_model_diagnose.py` first confirmed this fake model's arithmetic is exactly reproducible regardless of batch shape (max abs diff 0.0 at every position tested) — ruling out the possibility that its own results could vary by chance. Against this zero-noise model, the first version of the cache implementation scored 72/144 (all 36 greedy cases passed, all 36 sampling cases failed) — since there is no noise source, this result is proof of a logic bug, not evidence of noise. `p5_kv_cache_fake_model_trace.py` then drove both implementations round-by-round and showed the draft-side probabilities silently diverging starting round 1, pinpointing the crop-target line.

Fixing the crop target surfaced a second, related bug: `draft_propose_cached`'s loop samples the gamma-th draft token but (by design, matching the non-cached original) never feeds it back into the draft model, so on a fully-accepted round the draft cache was one position short of the corrected target. Fixed by feeding that one token through the draft model once more before cropping — a pure cache-sync forward pass with no generator draw, so it cannot affect sampling parity, only cache bookkeeping.

After both fixes: `p5_kv_cache_fake_model_verify.py` scores **144/144** (greedy and sampling, exact match — the strongest correctness signal available, since this model has no noise to hide behind), and the real-model `p5_kv_cache_verify.py` scores **18/18** (previously 9/18, with every sampling case failing).

### 3.2 Speed, before and after the fix

| | Before fix | After fix |
|---|---|---|
| Speedup, cached vs. no-cache (400 new tokens, gamma=5, 3 runs) | 1.651x | **3.861x** |
| Cached wall time (mean, 3 runs) | 47.04s | 15.44s |
| No-cache wall time (mean, 3 runs) | 77.66s | 59.60s |

### 3.3 Length-dependence (60-token crossover still unconfirmed; 400-token breakdown now re-measured)

At a short generation length (60 tokens), the cached implementation measured *slower* than no-cache (0.70–0.80x) even before the bugfix was found; only at 400 tokens did it become faster (1.65x, pre-fix). A time-breakdown (`p5_kv_cache_profile.py`) attributed this to per-call MPS dispatch overhead dominating at short lengths, while no-cache's cost of fully reprocessing a growing history dominates at long lengths.

That 60-token finding turned out to rest on a shakier foundation than it looked: `p5_kv_cache_profile.py`, at the time, was its own **hand-duplicated, standalone reimplementation** of both the cached and non-cached generation loops (written for instrumentation purposes), not a caller of the real `speculative_generate`/`speculative_generate_cached`. That duplicate copy was never updated when Section 3.1's crop-target bug was found and fixed — it silently kept the *original*, buggy crop formula. Re-running it post-fix at 400 tokens (unchanged) initially reproduced this: a nonsensical 1.19x, with a suspiciously bloated "unaccounted" bucket on the cached side — the tell that something in the harness itself, not the model, was wrong.

The script has since been rewritten (2026-09-05) to call the real, verified implementations directly, with draft/target/crop timing obtained by temporarily monkey-patching the relevant module-level functions rather than hand-copying the algorithm a second time — the same anti-duplication fix as Section 5's DRY refactor, applied to the benchmark harness instead of the implementation. Re-run at 400 tokens with the corrected script: **3.594x** (no-cache 67.63s, cached 18.82s), consistent with `p5_kv_cache_speedup.py`'s independently-measured 3.861x/4.400x. Crop time is negligible either way (0.012s total across ~80 rounds) — it was never the bottleneck.

**The original 60-token "cache is slower" claim itself has NOT been re-measured with the corrected script** — since it was produced by the same buggy duplicate harness, it should be treated as unconfirmed rather than either re-affirmed or assumed false. This re-test was deliberately deferred (in favor of moving on to P5.3) and is flagged here as an open item, not silently dropped.

### 3.4 A useful cross-check that motivated the deeper investigation

A separate cached-vs-no-cache ablation of the target model *alone* (no speculative decoding, no draft model at all — `p5_kv_cache_target_only.py`) measured a real 1.61x speedup from caching even at just 64 tokens. Comparing that to the pre-fix full pipeline's slowdown at a similar length (0.70–0.80x) showed the caching *primitive* itself was sound, and that whatever was eating the benefit was specific to how the speculative-decoding loop used it — which is what motivated building the fake-model tests in the first place, rather than accepting the length-dependence story in Section 3.3 as the final answer.

### 3.5 Additional adversarial verification and a reproducibility re-check (post-commit)

After the bugfix above was committed (`33e7433`), the user asked for more testing before trusting the result, rather than accepting 144/144 as the final word. Three additional, non-redundant checks were run:

1. **Harder adversarial fake-model sweep.** `p5_kv_cache_fake_model_verify.py` was extended with two more extreme draft/target phase gaps (in addition to the original 0.6 "normal" and 2.4 "high-rejection-stress" gaps: 3.14159265 "extreme-opposite-phase" and 6.0 "extreme-high-freq-shift"), pushing draft/target disagreement — and therefore the reject/resample/rollback path — harder than the original sweep did. Result: **288/288** (up from 144 cases in the original sweep, now at 4 phase gaps instead of 2).
2. **EOS-mid-block truncation-parity test.** The original 144/288-case sweep never produced an EOS token, so it never exercised truncation at all. A new `EOSFakeModel` forces EOS to land in the *middle* of an accepted gamma=5 block (not at a round boundary) via a dominating logit override, and checks that `speculative_generate` and `speculative_generate_cached` truncate their output at exactly the same point. Result: **24/24**. Combined with (1): **312/312** — see `results/p5_kv_cache_fake_model_verify_extended_result.json`.
3. **Reproducibility of the 3.86x speedup under a different random seed batch.** `p5_kv_cache_speedup.py` was re-run unmodified except for `BASE_SEED` (400 → 900). Result: no-cache 64.76s ± 18.18, cached 14.72s ± 1.02, speedup **4.400x** (vs. 3.861x for the original seed batch). The cached path is stable across both seed batches (~14.7–15.4s); the no-cache path is noisy (~18–19s std, consistent with the MPS per-call-overhead hypothesis in Section 3.3), which is why the point-estimate speedup moves between runs — but every individual per-run ratio in both seed batches is ≥3.5x, and none come close to contradicting the "at least ~3.5–4x" conclusion. See `results/p5_kv_cache_speedup_400_seed900_result.json`.

None of these three checks found a new problem. Taken together with 3.1–3.4, this is now: a proof of correctness under adversarial conditions (not just typical ones), explicit coverage of a previously-untested code path (EOS truncation), and confirmation that the headline speedup number is not a one-off favorable random draw.

## 4. Interpretation

The core lesson of this milestone is methodological, not just numerical: **the project's existing "greedy = zero tolerance, sampling = statistical" correctness standard (established in v1.0's P1.2/P1.3) is not strong enough on its own to catch every class of cache bug.** A bug that only ever manifests through *which candidate gets rejected*, never through *what the fallback token is*, hides completely behind greedy mode's insensitivity to the specific (wrong) value a rejected proposal held. It took a deterministic, zero-noise synthetic model — built specifically to remove floating-point noise as a possible explanation — to convert "sampling mode disagrees, and we think that's expected" from an inference into a provable fact, and only then to find that the "expected" explanation was actually wrong.

The magnitude of the fix (1.65x -> 3.86x, more than doubling the previously-measured speedup) is consistent with the mechanism: a draft model proposing tokens from the wrong absolute position produces proposals that are close to uncorrelated with what the target model actually expects, tanking the real acceptance rate. The implementation was, in effect, paying nearly the full draft-side compute cost of speculative decoding for close to none of its benefit, for every round after the first.

A second, smaller lesson from Section 3.5: a single "144/144" or "312/312" run is a snapshot, not a guarantee, when the thing being measured (wall-clock speed) has a noisy component. Re-running with a different seed batch, and deliberately trying to break the same test harder (more extreme phase gaps, forcing an untested code path), is cheap relative to the cost of shipping a wrong headline number.

## 5. Honest caveats

- **The earlier "benign floating-point noise" diagnosis (`scripts/debug/p5_kv_cache_diagnose.py`, cited in this project's own working notes) was wrong**, or at least not the operative explanation for the sampling-mode mismatches it was invoked to explain. It is being left in the repo rather than deleted, with this report as the correction, per the project's own standing principle that a diagnosis being wrong is worth recording, not quietly erasing (project_plan_v9.md §9.6's spirit, even though this specific case — a diagnosis script producing a misleading conclusion rather than a numeric error — isn't one of the plan's originally enumerated integrity risks). Genuine floating-point non-associativity between batched and incremental compute almost certainly still exists at some much smaller scale (consistent with the ~1e-3 max-abs-diff that script measured), but it was not the cause of the divergence pattern actually observed.
- Section 3.3's 60-token length-crossover finding remains unconfirmed after the bugfix -- not because it hasn't been re-run, but because the tool used to measure it (`p5_kv_cache_profile.py`) was itself found to be a stale, hand-duplicated copy of the algorithm still carrying the original crop-target bug (see Section 3.3). The tool has been fixed (now calls the real implementation via monkey-patched timers) and re-confirmed at 400 tokens (3.594x, consistent with the standalone speedup benchmark), but the 60-token case specifically has not yet been re-run with the corrected tool. This is a second, independent instance of the same root cause as Section 3.1's bug -- hand-duplicated logic silently drifting from a fix made elsewhere -- and is recorded here for the same reason: worth noticing the pattern, not just the individual bugs.
- `p5_kv_cache_speedup.py`'s post-fix runs still show `outputs match: False` for some 400-token sampling-mode generations, even after the logic bug fix — and this reproduced again under the independent seed-900 re-run (2 of 3 runs mismatched, same as the seed-400 run). Given the fake-model test now proves the underlying bookkeeping correct by construction (including under adversarial phase gaps, Section 3.5), and the real-model 40-token verify script matches 18/18 exactly, the most likely explanation is genuine (and now much smaller) floating-point noise finally having enough rounds (400 tokens is ~10x longer than the verify script's test) to occasionally flip one sampled draw. Seeing a similar mismatch *rate* under a completely different seed batch is mildly reassuring (a rate around 1/3 to 2/3 rather than either 0 or 100%) but this has not been separately re-diagnosed the way the original (larger, since-explained) divergence was, and is flagged here rather than asserted.
- All benchmark numbers in this report use a single model pair, on one Mac, at n_runs = 3 (per-run standard deviations are reported where available and are sometimes a large fraction of the mean — see the underlying `results/p5_kv_cache_*.json` files).
- The scripts in this milestone now number eight, split by role and folder: `scripts/debug/p5_kv_cache_diagnose.py`, `scripts/debug/p5_kv_cache_fake_model_diagnose.py`, and `scripts/debug/p5_kv_cache_fake_model_trace.py` are one-time forensic/diagnostic tools (their job — finding and justifying the bug fix above — is done, and they are not meant to be re-run as regression tests going forward), physically separated into `scripts/debug/` for exactly that reason; `p5_kv_cache_fake_model_verify.py` and `p5_kv_cache_verify.py` (in `scripts/`) are the ongoing regression tests; `p5_kv_cache_speedup.py`, `p5_kv_cache_profile.py`, and `p5_kv_cache_target_only.py` (also in `scripts/`) are the performance benchmarks.

## 6. What's next

With a verified-correct, and now genuinely fast, KV cache in place, the path to P5.3 (batch-aware circuit breaker) is unblocked: P5.3 needs a real, measured cache-rebuild/switching cost (to compare against Nightjar's reference range of 17.87–102.03ms), and this milestone's cache primitives (`_forward_step`, `_crop_cache`) are the building blocks for measuring exactly that cost when the circuit breaker disables and later re-enables speculative decoding. Also completed since the first version of this report: the scripts-folder reorganization (Section 5), a DRY refactor removing the hand-duplicated crop-target formula, and a rewrite of `p5_kv_cache_profile.py` after discovering it was itself a second hand-duplicated (and stale) copy of the algorithm (Section 3.3). Still pending: re-running the corrected profiler at 60 tokens specifically, to actually re-confirm (or overturn) Section 3.3's original length-crossover claim -- deliberately deferred in favor of starting P5.3 next.
