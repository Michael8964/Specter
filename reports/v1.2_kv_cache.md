# Specter — Milestone Report v1.2: Incremental KV-Cache for Speculative Decoding

**Scope:** P5.3 prerequisite (Track/Pillar 5)
**Status:** Complete, verified by direct execution, including a root-cause bug fix found mid-investigation
**Models used in this milestone:** draft = Qwen2.5-0.5B-Instruct, target = Qwen2.5-1.5B-Instruct (same pair as v1.0/v1.1)

## 1. Summary

v1.1 identified that `draft_propose`/`target_verify` (the v1.0 core) recompute attention over the *entire* growing sequence on every single call, with no cache at all — and flagged this as a hard blocker for P5.3, which requires measuring a real KV-cache rebuild/switching cost. This milestone adds an incremental, `past_key_values`-based cache (`src/speculative_decode_kv.py`) that reuses cached Key/Value tensors instead of recomputing them, with correct rollback when speculative candidates are rejected.

The investigation did not go in a straight line, and the crooked path is the most useful part of this report. The first working version passed every *greedy-mode* correctness check but was **slower** than the uncached baseline at short generation lengths, and only modestly faster (1.65x) at long ones. A deeper, harder-to-fool verification method — a synthetic model whose output depends only on absolute token position, with zero floating-point noise — proved that the sampling-mode mismatches we had earlier (incorrectly) diagnosed as "benign floating-point noise" were actually a real logic bug: the draft cache's rollback target was missing a term that the target cache's (correct) rollback already had, silently wiping the cached prompt on round 0 and making every subsequent draft proposal be computed from the wrong absolute position. Greedy-mode correctness never caught this, because a rejection always falls back to the (correctly cached) target model's own token regardless of what the mispositioned draft proposed. Fixing it raised the measured speedup at 400 tokens from **1.65x to 3.86x**.

## 3. Results

### 3.1 The bug, and how it was found

`speculative_decoding_step_cached` rolls both caches back after each round to discard rejected candidates. The target cache's rollback target was `target_start_len + target_seed_ids.shape[1] + n_accepted` (correct). The draft cache's was `draft_start_len + n_accepted` — **missing the seed-length term**. On round 0 (`draft_start_len = 0`, a rejection so `n_accepted = 0`), this cropped the draft cache to length 0, discarding the just-cached prompt entirely. From round 1 onward, the draft model's `position_ids` were then computed from that wrong (too-small) cache length, so every later draft proposal was generated from the wrong absolute position in the sequence.

This was invisible to `p5_kv_cache_verify.py`'s greedy-mode check (9/9 pass, both before and after the fix) because greedy mode's output on any rejection is the target model's own greedy token — computed from the correctly-tracked target cache, independent of whatever the mispositioned draft actually proposed. The bug degraded the draft's real usefulness without ever producing a wrong *greedy* output token.

It was caught by `p5_kv_cache_fake_model_verify.py`: a synthetic model whose logits are a deterministic function of absolute position only (`sin`/`cos` of position and vocab index, no learned weights, no attention). `p5_kv_cache_fake_model_diagnose.py` first confirmed this fake model's arithmetic is exactly reproducible regardless of batch shape (max abs diff 0.0 at every position tested) — ruling out the possibility that its own results could vary by chance. Against this zero-noise model, the first version of the cache implementation scored 72/144 (all 36 greedy cases passed, all 36 sampling cases failed) — since there is no noise source, this result is proof of a logic bug, not evidence of noise. `p5_kv_cache_fake_model_trace.py` then drove both implementations round-by-round and showed the draft-side probabilities silently diverging starting round 1, pinpointing the crop-target line.

Fixing the crop target surfaced a second, related bug: `draft_propose_cached`'s loop samples the gamma-th draft token but (by design, matching the non-cached original) never feeds it back into the draft model, so on a fully-accepted round the draft cache was one position short of the corrected target. Fixed by feeding that one token through the draft model once more before cropping — a pure cache-sync forward pass with no generator draw, so it cannot affect sampling parity, only cache bookkeeping.

After both fixes: `p5_kv_cache_fake_model_verify.py` scores **144/144** (greedy and sampling, exact match — the strongest correctness signal available, since this model has no noise to hide behind), and the real-model `p5_kv_cache_verify.py` scores **18/18** (previously 9/18, with every sampling case failing).

### 3.2 Speed, before and after the fix

| | Before fix | After fix |
|---|---|---|
| Speedup, cached vs. no-cache (400 new tokens, gamma=5, 3 runs) | 1.651x | **3.861x** |
| Cached wall time (mean, 3 runs) | 47.04s | 15.44s |
| No-cache wall time (mean, 3 runs) | 77.66s | 59.60s |

### 3.3 Length-dependence (measured before the bugfix; not yet re-measured after)

At a short generation length (60 tokens), the cached implementation measured *slower* than no-cache (0.70–0.80x) even before the bugfix was found; only at 400 tokens did it become faster (1.65x, pre-fix). A time-breakdown (`p5_kv_cache_profile.py`) attributed this to per-call MPS dispatch overhead dominating at short lengths, while no-cache's cost of fully reprocessing a growing history dominates at long lengths. This mechanism is still real and worth keeping in mind, but Section 3.1's bug was, in retrospect, likely also suppressing the *effective* speedup at every length tested (a degraded acceptance rate hurts a short run and a long run alike) — this breakdown has not been re-run after the fix, so the exact post-fix crossover point is an open question, not a re-confirmed one.

### 3.4 A useful cross-check that motivated the deeper investigation

A separate cached-vs-no-cache ablation of the target model *alone* (no speculative decoding, no draft model at all — `p5_kv_cache_target_only.py`) measured a real 1.61x speedup from caching even at just 64 tokens. Comparing that to the pre-fix full pipeline's slowdown at a similar length (0.70–0.80x) showed the caching *primitive* itself was sound, and that whatever was eating the benefit was specific to how the speculative-decoding loop used it — which is what motivated building the fake-model tests in the first place, rather than accepting the length-dependence story in Section 3.3 as the final answer.

## 4. Interpretation

The core lesson of this milestone is methodological, not just numerical: **the project's existing "greedy = zero tolerance, sampling = statistical" correctness standard (established in v1.0's P1.2/P1.3) is not strong enough on its own to catch every class of cache bug.** A bug that only ever manifests through *which candidate gets rejected*, never through *what the fallback token is*, hides completely behind greedy mode's insensitivity to the specific (wrong) value a rejected proposal held. It took a deterministic, zero-noise synthetic model — built specifically to remove floating-point noise as a possible explanation — to convert "sampling mode disagrees, and we think that's expected" from an inference into a provable fact, and only then to find that the "expected" explanation was actually wrong.

The magnitude of the fix (1.65x -> 3.86x, more than doubling the previously-measured speedup) is consistent with the mechanism: a draft model proposing tokens from the wrong absolute position produces proposals that are close to uncorrelated with what the target model actually expects, tanking the real acceptance rate. The implementation was, in effect, paying nearly the full draft-side compute cost of speculative decoding for close to none of its benefit, for every round after the first.

## 5. Honest caveats

- **The earlier "benign floating-point noise" diagnosis (`p5_kv_cache_diagnose.py`, cited in this project's own working notes) was wrong**, or at least not the operative explanation for the sampling-mode mismatches it was invoked to explain. It is being left in the repo rather than deleted, with this report as the correction, per the project's own standing principle that a diagnosis being wrong is worth recording, not quietly erasing (project_plan_v9.md §9.6's spirit, even though this specific case — a diagnosis script producing a misleading conclusion rather than a numeric error — isn't one of the plan's originally enumerated integrity risks). Genuine floating-point non-associativity between batched and incremental compute almost certainly still exists at some much smaller scale (consistent with the ~1e-3 max-abs-diff that script measured), but it was not the cause of the divergence pattern actually observed.
- Section 3.3's length-crossover finding was measured *before* the bugfix and has not been re-run after it; the qualitative mechanism (fixed per-call overhead vs. growing-reprocess cost) is plausible on its own grounds but the specific crossover point is now unconfirmed.
- `p5_kv_cache_speedup.py`'s post-fix run still shows `outputs match: False` for its 400-token sampling-mode generations, even after the logic bug fix. Given the fake-model test now proves the underlying bookkeeping correct by construction, and the real-model 40-token verify script now matches 18/18 exactly, the most likely explanation is genuine (and now much smaller) floating-point noise finally having enough rounds (400 tokens is ~10x longer than the verify script's test) to occasionally flip one sampled draw — but this has not been separately re-diagnosed the way the original (larger, since-explained) divergence was, and is flagged here rather than asserted.
- All benchmark numbers in this report use a single model pair, on one Mac, at n_runs = 3 (per-run standard deviations are reported where available and are sometimes a large fraction of the mean — see the underlying `results/p5_kv_cache_*.json` files).

## 6. What's next

With a verified-correct, and now genuinely fast, KV cache in place, the path to P5.3 (batch-aware circuit breaker) is unblocked: P5.3 needs a real, measured cache-rebuild/switching cost (to compare against Nightjar's reference range of 17.87–102.03ms), and this milestone's cache primitives (`_forward_step`, `_crop_cache`) are the building blocks for measuring exactly that cost when the circuit breaker disables and later re-enables speculative decoding.
