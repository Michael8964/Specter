# Specter — Milestone Report v1.0: Speculative Decoding Core

**Scope:** P1.0 – P1.4 (Track A)
**Status:** Complete, verified by direct execution (not by code review alone)
**Models used in this milestone:** draft = Qwen2.5-0.5B-Instruct, target = Qwen2.5-1.5B-Instruct
*(Qwen2.5-1.5B-Instruct is a temporary stand-in for the project's planned Qwen2.5-3B-Instruct target, adopted to keep iteration fast during development. The correctness properties established in this report — greedy equivalence, fault-injection coverage, statistical convergence of the accept/reject test — are properties of the algorithm's implementation and are expected to hold under any draft/target pair with a shared tokenizer; the specific numeric results below (alpha, acceptance-length curve) are specific to this pair and will be re-measured once the final 3B target is in place.)*

## 1. Summary

This milestone implements and verifies the core algorithm behind speculative decoding (Leviathan et al., 2023, *"Fast Inference from Transformers via Speculative Decoding"*, arXiv:2211.17192): a small "draft" model proposes several candidate tokens ahead of time, and a larger "target" model verifies all of them in a single forward pass, accepting the ones it agrees with and only falling back to its own generation where it doesn't. Done correctly, this produces **exactly the same output distribution** as running the target model alone, while requiring fewer expensive target-model forward passes per output token.

"Correctly" is the operative word, and it is also the theme of this milestone: three real, distinct bugs were found and fixed during development — not through code review, but by actually running the implementation and comparing its output against an independent reference. Rather than stop at "the tests pass now," this milestone goes one level deeper and asks whether the verification method itself can be trusted: a fault-injection test deliberately reintroduces each of those bugs and confirms the verifier actually catches them, and a statistical test confirms the sampling-mode accept/reject logic converges to its theoretical acceptance rate rather than just "looking plausible" on a handful of examples.

| Stage | Deliverable | Purpose |
|---|---|---|
| P1.0 | `scripts/p1_gate.py`, `scripts/p1_acceptance.py`, MLX cross-check scripts | Front gate: confirms the draft/target pair shares a tokenizer, and estimates whether they agree with each other often enough for speculative decoding to be worthwhile at all. |
| P1.1 | `src/speculative_decode.py` (`draft_propose`, `target_verify`, `speculative_decoding_step`, `speculative_generate`) | The core algorithm: autoregressive draft proposal, single-pass target verification, accept/reject/resample/bonus-token logic, for both greedy and sampling modes. |

| P1.4 | `scripts/p1_gamma_scan.py` | Characterizes how the number of tokens produced per verification round changes as gamma (the number of candidates proposed per round) is varied from 1 to 10. |

## 3. Results

### 3.1 Front gate (P1.0)

- Tokenizer vocabularies match exactly (151,665 tokens on both sides).
- Greedy-mode token agreement between draft and target: 94% (47/50).
- Theoretical acceptance rate, **alpha = E[min(p_draft, p_target)]**, averaged over 120 contexts: **0.7685** (range 0.2222–0.9998), cross-validated against an independent MLX implementation (0.7663, difference 0.0022).
- Gate decision: **PASS** (threshold 0.65) — this pair is a reasonable candidate for speculative decoding.

### 3.2 Correctness (P1.2)

After fixing the bugs described in Section 4, the speculative decoder reproduces the target model's independent greedy decoding with **100% token-for-token agreement across all 5 test prompts, 0 mismatched positions.**

### 3.3 Fault injection (P1.3a)

Three specific, previously-real bugs were deliberately reintroduced and tested against the same comparison methodology P1.2 uses:

| Injected fault | What it breaks | Detected? |
|---|---|---|
| `bonus_from_draft` | Bonus token sampled from the draft model instead of the target model | Yes (3/3 prompts) |
| `greedy_residual_resample` | Greedy-mode rejection reuses a formula that is only valid for sampling mode | Yes (2/3 prompts — see note below) |
| `swap_accepted_order` | Accepted tokens appended in reversed order | Yes (3/3 prompts) |

All three faults were caught. One instructive exception: `greedy_residual_resample` went undetected on one of three prompts, because the erroneous formula happened, by numerical coincidence, to select the same token the correct formula would have — a concrete illustration of why a verifier should not be trusted based on a single passing run.

### 3.4 Statistical validation (P1.3b)

Measured across the same 120 contexts used for the theoretical alpha above, with 300 independent accept/reject trials per context:

- Theoretical mean alpha: **0.7685**
- Pooled empirical acceptance rate (36,000 total trials): **0.7715** (gap: 0.003)
- Contexts whose empirical rate fell within a ~95% statistical margin of the theoretical value: **108/120 (90%)**

The 12 contexts outside the margin were examined individually rather than treated as failures by default: 5 were an artifact of the standard-error formula breaking down when the empirical rate hit exactly 1.0 (a known limitation of the Wald interval near probability boundaries), and 7 were consistent with the ~5% false-positive rate expected from running 120 independent 95%-confidence checks (a multiple-comparisons effect). The aggregate match (0.7685 vs. 0.7715) is the stronger evidence of correctness.

### 3.5 Gamma characterization (P1.4)

Mean tokens produced per verification round (== per expensive target-model forward pass), for gamma in {1, 3, 5, 7, 10}:

| gamma | Mean round length | Total rounds sampled |
|---|---|---|
| 1 | 1.697 | 119 |
| 3 | 3.045 | 67 |
| 5 | **3.980 (peak)** | 51 |
| 7 | 3.942 | 52 |
| 10 | 3.904 | 52 |

The curve rises sharply then plateaus around gamma=5, consistent with the expected trade-off: larger gamma raises the theoretical per-round ceiling (gamma+1) but lengthens the chain of candidates that must all survive verification in sequence, so gains diminish and can mildly reverse. Every measured value stayed below the theoretical asymptote implied by alpha (1/(1-alpha) ≈ 4.32), which is a sanity check the implementation passes. Sample sizes shrink as gamma grows (a fixed token budget is consumed in fewer, longer rounds), so the small dip from gamma=5 to gamma=10 should be read as suggestive, not conclusive — a larger controlled experiment would be needed to confirm it as a real effect rather than noise. Note that this curve measures token throughput only, not wall-clock time: gamma also controls how many sequential draft-model forward passes are spent per round regardless of outcome, so the true efficiency-optimal gamma will only be known once wall-clock throughput is measured directly (planned, not yet done).

## 4. Bugs found and fixed

Finding real bugs — and being able to explain exactly how they were found — is often more informative in an interview than a clean success story. All three were found by running the code and comparing against an independent reference, not by inspection:

1. **MPS/CPU `torch.Generator` device mismatch.** Sampling was crashing on Apple Silicon because the random generator and the probability tensor lived on different devices. Fixed by always performing the final sampling step on CPU — the model's forward pass still runs on the accelerator; only the last, cheap sampling step moves.

2. **Wrong rejection formula in greedy mode.** The paper's residual-resampling formula (`norm(max(0, p_target - p_draft))`) is only proven correct for *sampling* mode. It was mistakenly reused in greedy mode as well, where the correct behavior is to output the target model's own argmax directly. A constructed counterexample (`p_target={A:0.5,B:0.3,C:0.2}`, `p_draft={A:0.49,B:0.01,C:0.5}`) shows the two formulas can disagree. This is exactly the bug reintroduced deliberately in Section 3.3's fault-injection test.

3. **Bonus-token budget overshoot.** A single round of speculative decoding can legitimately produce up to `gamma + 1` tokens (the extra one being the "bonus" token awarded when every candidate is accepted). The generation loop capped `gamma` at the remaining token budget but didn't also cap the *bonus token* at that budget, so the final round of a generation could silently overshoot `max_new_tokens` by exactly one token. This was initially misdiagnosed as an EOS-handling bug (the symptom — output exactly one token too long — looked similar); the misdiagnosis was caught because the "fix" was re-tested and produced identical results, proving it hadn't changed anything.
