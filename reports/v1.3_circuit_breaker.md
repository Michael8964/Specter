# Specter — Milestone Report v1.3: P5.3 Batch-Aware Circuit Breaker

**Scope:** P5.3 (Track/Pillar 5)
**Status:** Complete against project_plan_v9.md's three hard requirements; end-to-end integration into a live generation loop intentionally deferred (see Section 6)
**Models used for the real-cost measurement:** draft = Qwen2.5-0.5B-Instruct, target = Qwen2.5-1.5B-Instruct (same pair as v1.0–v1.2)

## 1. Summary

project_plan_v9.md (line 184) specifies three hard requirements for P5.3: (a) automatically degrade/disable speculative decoding at high batch load, (b) a periodic re-probe mechanism that avoids DSD's "reactivation difficulty," and (c) a **real, measured** KV-cache rebuild/switching cost, compared against Nightjar's reported 17.87–102.03ms range — explicitly not assuming switching is free, per the plan's own critique of BanditSpec's approach. This milestone builds all three as two independently testable pieces: a pure control-logic circuit breaker state machine (`src/circuit_breaker.py`), and a real-model measurement of the one unavoidable cost that state machine's reactivation triggers (`scripts/p5_circuit_breaker_switch_cost.py`).

A design decision was made before writing any code: how to obtain the "current batch size" signal the circuit breaker reacts to. Two options were weighed — a simplified, externally-controlled proxy signal (**Option A**) versus building a real multi-sequence concurrent-serving harness (**Option B**, closer to what the friend's P6.1 code and EQSPEC's "rectangular invariant" design do). **Option A was chosen**: a real concurrent-serving harness is properly the job of the still-unstarted P4 (Batch Size crossover experiment) pillar, not P5.3 — building a half-measure version of it here risked redoing the work when P4 is actually tackled. This also resolved an adjacent question that came up mid-design: whether cloud GPU rental was needed for this. It is not — project_plan_v9.md itself scopes even the *full* P4 batch experiment as Mac-local (its own Stage 5); cloud GPU rental (Stage 6, $30–50 budget) is reserved for the AWQ-vs-GPTQ real-speed comparison, the vLLM baseline (broken on Mac — measured 3–5 tok/s in CPU mode vs. 92 tok/s for llama.cpp Metal), the BitsAndBytes CUDA-only control arm, and the BanditSpec baseline code — none of which P5.3 touches.

## 2. What was built

| Component | Purpose |
|---|---|
| `src/circuit_breaker.py` | `CircuitBreakerConfig` + `SpeculativeCircuitBreaker`: a pure state machine (`SPECULATIVE` / `DISABLED`) with two independent guards against flapping — a hysteresis gap (`enable_threshold < disable_threshold`) and a minimum dwell time before re-enabling is even considered. It has no real cost of its own: it decides *when* to reactivate, never performs the reactivation itself. |
| `scripts/p5_circuit_breaker_verify.py` | 8 deterministic scenarios (never-crosses-threshold, clean ramp, spike-then-immediate-drop, hysteresis-band hovering, boundary/flapping resistance, `probe_interval_steps > 1`, multiple disable/reactivate cycles, invalid-config rejection), each with a hand-computed expected event sequence — same "no randomness, no excuse for a mismatch" standard as `p5_kv_cache_fake_model_verify.py`. **8/8 passed.** |
| `scripts/p5_circuit_breaker_switch_cost.py` | Measures the one real cost the circuit breaker's reactivation triggers: the draft model's one-shot catch-up forward pass over however many tokens the target model generated alone while speculative decoding was disabled. The target side has zero rebuild cost of its own — it never stops running its own cache while disabled, it just keeps decoding autoregressively (identical to `p5_kv_cache_target_only.py`). Only the draft model's cache falls stale and needs the catch-up feed. |

## 3. Results

### 3.1 Real KV-cache rebuild cost, vs. Nightjar's 17.87–102.03ms

The first attempt (`n_runs=5`, one single global warm-up) was too noisy to trust: some gap sizes had a standard deviation *larger than the mean*, and results were non-monotonic in gap size (a gap of 5 tokens measured slower than a gap of 20). Root-caused to Apple's MPS backend most likely JIT-compiling a kernel graph the first time it sees a given input shape, so a gap size's very first timed call was silently paying a one-time compile cost indistinguishable, in the original script, from steady-state cost. Fixed by warming up **each gap size individually** (untimed) before timing it, and raising `n_runs` to 15.

| Gap (tokens missed while disabled) | Median rebuild cost | Std | vs. Nightjar (17.87–102.03ms) |
|---|---|---|---|
| 1 | 14.98ms | 0.81ms | below range |
| 5 | 16.53ms | 0.66ms | below range |
| 10 | 18.30ms | 0.18ms | within range |
| 20 | 20.69ms | 0.13ms | within range |
| 50 | 23.91ms | 0.65ms | within range |
| 100 | 31.55ms | 1.70ms | within range |

Std is roughly 1–8% of the mean at every gap size after the fix — clean, monotonic, and trustworthy, unlike the first attempt. Small gaps (missing only 1–5 tokens) rebuild faster than Nightjar's reported range; from 10 missed tokens onward, our (0.5B/1.5B, Mac MPS) pair's measured cost falls within Nightjar's published range. This is not a claim that our numbers should exactly match a different paper's different hardware and models — it is a sanity check that our measured order of magnitude is a plausible, comparable one, not wildly off in either direction.

### 3.2 Circuit breaker state machine correctness

All 8 scenarios passed with zero mismatches against hand-computed expected event sequences. Two design choices were specifically exercised: the hysteresis gap prevents reactivation while the batch signal hovers between the two thresholds without ever dropping far enough (Scenario 4: batch drops from 8 to 6 and stays there — 6 is below the disable threshold of 8 but above the enable threshold of 4, so it correctly never reactivates), and the minimum dwell time prevents an immediate reactivation even when the batch signal would otherwise allow it the very next step after disabling (Scenario 3: batch spikes to 8 then immediately drops to 1, but reactivation is still held off until the dwell period elapses). These directly address the plan's "avoid DSD-style reactivation difficulty" requirement, which on inspection is really two distinct failure modes — reactivating on stale/momentary good news, and flapping near a boundary — not one.

## 4. Interpretation

P5.3's three requirements decompose cleanly into "a control-flow decision" and "a real cost that decision incurs," and keeping those as two separately-verifiable pieces (rather than one entangled implementation) meant each could be tested at the appropriate standard: the state machine with exhaustive, deterministic, hand-computed scenarios (no model needed, no excuse for noise), and the real cost with an actual model measurement disciplined the same way v1.2's KV-cache work was — distrust a single noisy result, root-cause the noise, re-measure, and only then report a number.

The Option A vs. Option B decision is worth calling out as a scoping discipline exercise more than a technical one: it would have been easy to bolt a half-real concurrent-serving loop onto P5.3 "while we're at it," but that harness is properly P4's deliverable, and building a lesser version of it here would likely need to be redone rather than reused when P4 is actually tackled. Recognizing that a piece of work belongs to a *different*, not-yet-started part of the project — rather than doing a rushed version of it now because the code is already open — is its own kind of correctness.

## 5. Honest caveats

- The "batch size" signal feeding the circuit breaker in `scripts/p5_circuit_breaker_verify.py` is entirely synthetic/scripted — there is no real concurrent multi-sequence serving harness behind it. This is a deliberate scope decision (Option A over Option B, Section 1), not an oversight: producing that signal for real is the still-unstarted P4 pillar's job.
- `src/circuit_breaker.py` and `scripts/p5_circuit_breaker_switch_cost.py` are verified **independently** but have **not** been wired together into one live, end-to-end generation loop that actually performs the real cache catch-up exactly when the state machine reports a `"reactivated"` event. Each piece is separately correct; their integration as a whole is not yet built or tested.
- Section 3.1's numbers use one model pair, on one Mac, one 21-token prompt, `n_runs=15`. The gap sizes tested (1–100 tokens) are a reasonable range but an arbitrary choice; a real production system's actual disabled-duration distribution is unknown without the real batching harness noted above.
- Carried forward from v1.2: the 60-token length-crossover claim in `v1.2_kv_cache.md` Section 3.3 remains unconfirmed (deliberately deferred by the user in favor of starting P5.3).

## 6. What's next

Circle back to the two completely unstarted pillars — **P2 (AWQ quantization)** and **P3 (AgentBench-OS evaluation)** — per the earlier explicit decision to do the whole project single-handedly rather than leave them permanently deferred. **P4 (Batch Size crossover experiment, Mac-local per the plan)** is where Option B's real concurrent-serving harness belongs, whenever that pillar is tackled; the circuit breaker and switch-cost pieces built here are ready to be wired into a live generation loop at that point, fed by a real batch-size signal instead of a scripted one.
